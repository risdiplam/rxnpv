# RxNPV — orientation for Claude Code

Read this fully before making any change. It carries forward context from a long chat-based build process that has no other record — if it's not written here or in `docs/`, it doesn't exist anywhere Claude Code can see it.

## What this is, and the scope line that matters most

A desktop valuation sandbox and trial-outcome simulator for a retail biotech investor, built for one specific user's own use. The explicit, user-set scope: **"good enough to help a retail biotech investor improve their analyses. Doesn't need to be institutional grade, doesn't need to have every conceivable feature."**

This line should govern every future decision about what to build. It has already been used, explicitly, to decline several reasonable-sounding feature ideas (see "Deliberately not built" below). Treat a new feature request against this bar before starting it, and say so if something seems like it's drifting past it — that's the correct, previously-established response, not silent compliance.

macOS (Apple Silicon / arm64) only. Not tested on Intel. Not signed or notarized — deliberately decided against; see "Deliberately not built" below for why.

**Runs on Electron 44.4.4 (Chromium 152, Node 22).** Upgraded from 33.4.11 in September 2026. One consequence worth knowing before sharing the app with anyone: Electron 44 raised the bundle's `LSMinimumSystemVersion` from **11.0 to 13.0**, so the app no longer launches on macOS 12 or earlier. That is fine for this machine and would only matter for someone else's older Mac.

## Standing instruction: push to GitHub continuously, not in batches

This repo previously lived only on the user's local machine for the entire build history, under an earlier project name tied to a pseudonym the user has since moved away from. That entire history was deliberately squashed into a single clean commit (old commit objects actually garbage-collected locally, not just superseded by a new branch) and pushed as a fresh start into a brand-new empty GitHub repo under the user's real account (`risdiplam`) — an ordinary push, not a force-push, since there was nothing on the remote yet to conflict with — see the bottom of `docs/RxNPV_External_Suggestions_Tracker.md` for the full account of that rename and scrub.

The user has explicitly stated a standing preference, not a one-time request: **work continues to happen locally on this Mac (required — see "macOS only" above, this is a real Electron app that needs a real Mac to build/package/verify), but every meaningful unit of work gets committed and pushed to `github.com/risdiplam/rxnpv` before moving to the next thing.** The stated reason is a real, previously-articulated fear of catastrophic local data loss — losing the project entirely if something happens to this machine — and the fix is keeping GitHub continuously current rather than treating a push as an occasional, separate "let's back things up now" event.

This is durable authorization for routine commits and pushes on this project specifically (not a license to push other repos, and never a license to force-push over the public history again without being asked) — a future session does not need to re-ask before pushing ordinary work here. Still stop and ask before anything unusual: a force-push, rewriting history again, changing repo visibility, or anything that isn't just "commit and push what was just built."

Practical implication for how work should be sequenced: don't let more than one meaningful change sit uncommitted/unpushed. Build → verify → commit → push, then move to the next thing, rather than accumulating a long list of local-only changes to push at the end of a session.

## Architecture — read this before touching the build

**This is not built with a real bundler.** No webpack, no esbuild, no Vite, no ES module imports/exports anywhere. It's 49 plain JavaScript files, concatenated in a specific order into one giant inline `<script>` block inside `shell.html`, producing `electron/rxnpv.html` — the single file the Electron shell actually loads.

This was a pragmatic choice made out of necessity: the app was originally built entirely inside a Claude chat conversation, in a sandboxed environment with no real bundler tooling available. It works, it's been thoroughly tested in that form, and **changing it is a legitimate future improvement but a real, deliberate architecture decision** — not something to fix in passing while doing something else. If you do it, do it as its own isolated change with full re-verification, not bundled into a feature or bug fix.

Because there's no module system, every file relies on the global scope and on `MODULE_ORDER` (declared at the top of `build.js`) being exactly right. Function declarations hoist within the combined script, so a file can call a function defined later in the concatenation order — but `const`/`let`/`class` do not hoist, so anything read at module-evaluation time (not inside a function body) must come from something earlier in the list. **Do not reorder `MODULE_ORDER` without understanding this and re-running the full test suite.**

### Build commands

```bash
node build.js              # reassemble only -> electron/rxnpv.html
node build.js --package    # reassemble + full electron-builder package -> electron/dist/mac-arm64/RxNPV.app
node build.js --install    # --package, then also copies the result into /Applications/RxNPV.app
```

Quit the running app first if using `--install` — it overwrites the app bundle you're launching.

**The build names itself.** `build.js` prepends `var RXNPV_BUILD = { version, commit, dirty, built }` (version from `electron/package.json`, commit from `git rev-parse --short HEAD`, `dirty` when `src/`, `shell.html` or `build.js` have uncommitted changes) and the sidebar's foot shows it (`buildStampText()`). Commit before `--install` so the installed app names a real commit; a user's report quotes it.

`build.js` syntax-checks every source file individually before concatenating — a broken file gives a clear, isolated error here instead of an unreadable failure somewhere inside a 900KB combined blob.

**React is vendored, not fetched.** `electron/vendor/` holds React 18.3.1's UMD builds, committed to the repo and packaged into the app. They used to load from unpkg at runtime, which meant the app could not start at all without an internet connection — the scripts failed, `React`/`ReactDOM` were undefined, and the whole bundle (including `ErrorBoundary`, itself a React component) never ran, leaving a blank window with nothing to explain it. Don't reintroduce a CDN tag here.

**The CSP carries a hash of the bundle, so `build.js` must compute it.** `shell.html` has a `__SCRIPT_HASH__` placeholder inside its `Content-Security-Policy`; `build.js` fills it with the sha256 of the assembled inline script and refuses to write an output if the placeholder is missing. Two things about this are easy to get wrong, and both were: the hash must cover the script element's *exact* text — including the newline right after `<script>` — so it is extracted from the finished artifact rather than reconstructed from `combined`; and `'self'` does not match `file:` subresources in Chromium, so `file:` is named explicitly for the vendored scripts. **jsdom does not enforce CSP**, so the entire test suite stays green against a policy that blanks the real app. Any CSP change has to be verified against the packaged build — see "Verify inside the actual packaged binary" below.

### A real bug this project's own tooling caught, worth understanding before writing anything similar

`build.js` originally used `shell.replace('__SCRIPT__', combined)` — a plain string as the replacement argument. `String.prototype.replace()` treats certain `$`-prefixed sequences in a *string* replacement argument as special pattern tokens (`$&`, `` $` ``, `$'`, `$$`), even when the search pattern itself is a plain string, not a regex. `combined` is hundreds of KB of real application code, and it happens to contain the literal two-character sequence `$'` (from ordinary code: `'$' + formatNumber(...)` in `ts_app.js`) — which JavaScript silently reinterpreted as "everything after the match," splicing unrelated file content into the middle of a source file. The fix, now in place: pass a **function** as the replacement argument, not a string — a function's return value is always inserted verbatim. If you ever write code that does string-replaces-into-string with large, arbitrary content as the replacement, use a function. This is a real, previously-shipped-adjacent bug, not a hypothetical.

**The rNPV conventions the engine follows (September 2026 methodology fixes, `docs/RxNPV_rNPV_Methodology_Review.md`).** Researched before any change; do not undo one of these without reading the review. (1) **The probabilities carry failure; the discount rate is the cost of capital** (12–15% for clinical-stage biotech) — never a 20–50% "venture" rate with probabilities, and **Bear/Bull keep the same rate** (presets add 0; they vary share and odds). (2) **Corporate G&A is weighted by the odds the company is still going** (`computeCompanyActiveByYear` in dcfEngine.js): pre-commercial G&A × P(still developing or inside the wind-down) before launch; G&A on revenue-if-launched × P(launch) after. (3) **Tax, one program: P(launch) × the success case's tax after its own losses** (`taxedCaseCalendar` / `taxSuccessWorld`); several programs tax the odds-weighted flow, a stated approximation. (4) **Financing: cash and shares together, or not at all** — a projected raise adds its expected cash with its shares, each weighted by the odds the company is still there to raise (`applyDilutionPath`). (5) **Cash is as the last filing reported it, unless the user ticks "Roll the cash forward"** (`capitalStructure.carryCashForward`, off by default — the user's decision, October 2026: "the basic base, bull, and bear cases should just assume the most recent verified numbers"). `effectiveCapitalStructure()` applies the roll-forward when ticked; every capital-structure read goes through it. The cash date and monthly burn are kept either way (Cash Runway, the rough failure floor). Likewise the **rough "if it fails" estimate from the burn** (`theCase.failureFloor.method === "burn"`, off by default) replaces the stage-cost floor only when ticked, and never touches Bear/Base/Bull. (6) **Ex-US launches 1.5 years after the US** by default (`EXUS_LAUNCH_LAG_BENCHMARK`). (7) **Benchmark R&D is DiMasi 2016 phase cost** (`PHASE_COST_BENCHMARKS`), not trial-only cost. The Overview headlines "If it works" beside Bear/Base/Bull, because an odds-weighted Base was being read as the failure case. The independent rebuilds in `math_verification.js` implement each of these with their own formulas.

**Three things that keep a case from going stale (October 2026).** (1) **A modelled raise can be priced as "% below today's price"** (`futureRaise.priceMode = "discount"`, `discountPct`; `futureRaisePrice()` in capitalEngine.js) so it follows the stock — new cases start there; a case saved before the choice keeps its typed fixed price. (2) **A red flag when the Napkin peak and the full build's peak differ by more than 1.5x** (`napkinBuildPeakMismatch`), because only one is in the valuation and the other was silently ignored (the user's Stoke case carried a $2.5B typed peak against a $1.31B build). (3) **"Snapshot from the model"** on the Evidence Log writes the "What the model says (snapshot)" entry from the live engine (`buildModelSnapshot` in scenarioEngine.js: price, Bear/Base/Bull, peak revenue, price-implied odds vs the case's, if it works, the failure floor by the case's method, the top three drivers), as a dated entry; since October 2026 earlier dates are kept (`addModelSnapshot`: one per day, same day replaces) — a narrow reversal covering model snapshots only; versioned whole-case snapshots stay unbuilt. Worked-example notes on the Saved tab show the date they were written.

**The October 2026 product pass (Feature Map §11; build log Phase 52).** What it added, and the rules to keep:
- **Catalyst dates are windows.** `parseCatalystWindow` (helpers.js) reads a day, month, quarter, half, year or month range ("2027-03 to 2027-09"); `parseCatalystDate` is the window's END (overdue only once a window ends; the floor burns to the end). Runway vs. Catalyst never collapses a window: cash running out between start and end is its own state, "inside". Prose stays undated.
- **Pinned catalysts are a flag on a Calibration Log entry** (`entry.pin = { type, source, at, sharedTag }`), never a second object; `nextCaseCatalyst` reads pins first; closed-out entries (`entry.closeOut`) drop out of overdue and next-catalyst.
- **Freshness** (`computeFreshness`): price + `theCase.priceAsOf` (stamped when typed), cash + date + an EDGAR check for a newer filing (`newerFinancialFiling` / `checkNewerFiling`, desktop only — gated on `window.electronAPI.edgarFetch`, not `isDesktop`, so jsdom never calls it), next catalyst, odds source. Amber only for a price over 7 days old or a newer filing.
- **Simulator → case odds** writes win-in-the-expected-direction × the benchmark odds of every LATER step into `posOverridePct`, with the run in `program.posSource`; `posFromSimulator` is true only while the field still holds the written figure. Never write an assurance hit rate as a launch probability.
- **Facilities** (`atmUndrawn`, `debtUndrawn`, `milestoneExpected`, `shelfRemaining`, `facilitiesNote` on the capital structure) never touch the valuation; the shelf never enters the runway. `computeFinancingBridge` counts a raise the case already models.
- **Simulator:** `design.delayMonths` (piecewise hazard), `design.targetEvents` (readout timing); `summarizeObservedEffects`; Phase 2→3 factors are per-run arguments. A prior filled by a tool records `priorSource` and is cleared when typed over.
- **The decision memo** is `buildDecisionMemo` → `DecisionMemoSection` (report section `memo`, off by default). Every figure comes from the same functions as the Overview; no generated prose. "What would change my mind" is `theCase.memo`.
- **Options move** (`optionsImpliedMove`, `modelImpliedMove`, `readImpliedMove`) is typed in, never fetched; `theCase.optionsMove`.
- **Snapshots are dated** (`modelSnapshotLabel`, `addModelSnapshot`; same day replaces). **The IRA clock** (`program.ira`, `applyIraClock` in `getProgramRevenueResult`) has no default cut. **Condition merges** live in `rxnpv_condition_merges` (a backup data key). **Open Targets returns `APPROVAL`** for approved drugs — match `/APPROV/`.
- **No position sizing of any kind** — the user's decision (Feature Map §8).
- **A runway is read from today** (October 2026 audit). The balance is the filing's, so `computeForwardRunway` takes the months since `cashAsOf` off the path's runway (`monthsSinceCash`, `runwayMonthsFromCash`; nothing when the cash is rolled forward, which already brings it to today). Every runway reader inherits it: Cash Runway, Runway vs. Catalyst (which passes its own `now`), the financing bridge (it reads the path `monthsSinceCash` further on), the memo, the report, Portfolio and the runway-vs-launch red flag. Before this every runway ran long by the months since the filing while catalyst dates were counted from today. Runway vs. Catalyst also leaves out closed-out entries and windows that have ended (`pastCount`).

**PoS attribute modifiers (Thomas 2016) combine by overlap, not independence (September 2026).** Rare disease and selection biomarkers each lift the area benchmark by a ratio against Thomas's baseline; when both are set and push the same way, `computePoSModifiers` uses the stronger single ratio per phase (and the larger regulatory delta), not the product — the product put a Phase 2 neurology program at 74% odds of launch against ~34% for Thomas's own rare-disease cohort. Opposite-direction effects still multiply (they offset). Molecule type remains a separate multiplicative axis. The red flag and the program card say so.

**Two engine rules to keep (September 2026).** (1) **Stage odds always multiply back to posToLaunch** (`computeEffectivePoS`): revenue is weighted by posToLaunch and each stage's R&D by the odds of reaching it, so if the two disagree costs and revenue describe different paths. A stage past the 99% cap hands its excess to the others; only a target above 0.99^n (a literal 100% — every "if it works" figure) takes every stage past 99%. (2) **The reverse-solvers (implied PoS, share, revenue, timing) solve on the headline's per-share value, modelled raise included** — "the price implies X" means at X this page's fair value equals the price. Both are pinned in `math_verification.js`.

**A note on the three benchmark tables:** `POS_BY_AREA`, `TRIAL_COST_BY_AREA` and `TRIAL_DURATION_BY_AREA` come from different source papers and do not share a taxonomy — the same disease is "Neurology" in one and "CNS" in another, "Autoimmune" vs "Immunomodulation", "Infectious disease" vs "Anti-infective", "Urology" vs "Genitourinary". `THERAPEUTIC_AREAS` is the union of all of them, so the dropdown offers both halves of each pair. `AREA_ALIASES` in `helpers.js` maps the synonyms so picking either name finds the real area-specific benchmark instead of silently falling back to a generic average. If you add a benchmark table, check whether its area names need entries there.

**Section export — every section in every view, PNG / PDF / SVG / + Report.** Before September 2026 export stopped at a chart's edge: a PNG came out with no title, no headline figures, no caveats, and "Panel" was a screenshot of the *screen*, so anything scrolled out of view was lost. Now every card, tool, Reference Sheet card, Portfolio card, open input card and Simulation panel carries one `SectionExportBar` (in `helpers.js`) that exports **the whole section**, at full height regardless of the window. How it works: `serializeSection()` (in `exportEngine.js`) clones the section's DOM, carrying form values across, expanding scroll boxes, restoring truncated text (`data-full-text`) and dropping anything marked `data-no-export`. `render-section` in `main.js` then lays it out in an offscreen window with the app's own styles, and either prints it to a vector PDF or captures it to PNG via CDP with `captureBeyondViewport`. Things to know before touching it:
- **A section is declared, not threaded.** Mark a block `data-export-section` (or wrap it in `ExportSection`); the bar finds its section by walking up the DOM. `toolCard`, the Reference Sheet `card()`, `SectionCard` (only while open) and `ExportableBlock` (only when not already inside a section) do this for you. The Simulation side has no React tree, so `attachSimExportBars()` in `ts_app.js` mounts a bar into every `.panel` via a MutationObserver, and the bar reads cases off `window.rxnpvSimBridge` instead of `ReportContext`.
- **"+ Report" does one of two things.** On a Workspace section the report already renders live (revenue chart, cash flow, bridge, SOTP, scenarios: the `reportSection` prop), it toggles that live section, because a frozen copy next to a live one would drift. Everywhere else it stores a snapshot. Either way the case list is **re-read at click time**, since a Simulation bar is never re-rendered and writing back a stale case would silently discard edits.
- **The report's snapshot renderer is the one deliberate `dangerouslySetInnerHTML` in the app** (`ReportSnapshot` in `reportView.js`). It is bounded: the content is app-serialised, sanitised at capture **and again at render** (stored data is only as trustworthy as whatever last wrote localStorage), and the page CSP (hash-only scripts, no remote loads) backstops both. ## Conviction tools — the half of the app that is not valuation

A deliberate product decision made in September 2026: **not every feature has to feed the DCF.** The app is a conviction sandbox, and a tool that helps a retail investor understand the science or the trial earns its place whether or not a number flows from it into a valuation. Several of these deliberately do not.

- **Trial Decoder** (Tools → Live research). Paste an NCT; get the design in plain English — allocation, masking, comparator, arms, primary endpoint — plus what the architecture can and cannot establish, and design red flags. Filled a real hole: the app could already *search* trials and *watch* them for changes but could never *explain* one. All derived from registered CT.gov fields that were already arriving in every response and being discarded; where CT.gov is silent it says "not stated" rather than defaulting, so an unregistered masking field never reads as open label. Engine in `trialDecoder.js`, pure and unit-tested.
- **Results reader**, also inside the decoder, below a divider so the design is read first and the outcome second. One fetch, three panels: what the registered endpoints returned (with the sponsor's own effect estimate, interval, p-value and — surfaced deliberately — whether the comparison was superiority or non-inferiority), who finished and who left by arm, and the adverse events. Engine in `trialResults.js`, pure and unit-tested. Four rules make it safe: nothing infers which arm is the drug (groups are named as the sponsor named them, differences are signed, never editorialised); a measure reported across strata or categories is never collapsed into a headline the sponsor did not register; **deaths are never counted as dropout**, and neither is moving into an open-label extension; and every rate carries its denominator, with a reason the sponsor never filed shown as "not registered" rather than 0.0%.
- **Trial-design red flags**, inside the decoder. Note these are *separate from* `computeRedFlags()`, which checks the user's own modelling inputs and says nothing about the study. Don't merge them.
- **Target Dossier** (Open Targets). Human genetic support for a target, disease associations split by whether the evidence is genetic or inferred, and what drugs already exist against it. **Deliberately not wired into PoS** — an Open Targets association score is a weighted aggregate over very heterogeneous evidence, and presenting it as a probability input would be exactly the false precision this project avoids. If that ever changes it should be a deliberate decision, not a drift.
- **Analog effect-size board** (inside Trial Explorer). What effect sizes actually got *posted* in an indication — the reference class a modelled hazard ratio should be read against. Always reports its own denominators ("17 extractable of 50 with results") because a board that quietly drops what it cannot parse reads as the whole landscape.
- **Analog positioning**, on the effect-size board. Place any number — a modelled hazard ratio before a readout, or the one a trial just posted — in the distribution of what has actually been reported in that indication, as a rank with its denominator. This is what a thin-win check should be: a percentile of the real reference class, never a fixed threshold, because a thin effect in oncology and in a rare metabolic disease are not the same number.
- **Trial Watch change classification.** The snapshot diff covers thirteen fields (nine in `CTGOV_DIFF_FIELDS` plus four list comparisons — a test in `audit_regressions_test.js` holds this number to the code) (design, arms, eligibility, endpoints, why-stopped) and ranks each change by what it means: *high* = changes what the trial can establish, *medium* = changes the terms, *routine* = a trial doing what trials do. A baseline saved before a field was ever parsed is skipped rather than reported as a phantom amendment, and the UI says so.
- **Asset Program view** (Tools → Live research). Every registered trial for one drug at once, by phase, with the trials that stopped and their registered reasons broken out. Carries the **evidence-base checklist** — "18 of 37 with a registered allocation are randomised · 11 blinded · 15 with posted results · largest n=815" — which is deliberately a set of counts with their own denominators and **never a composite score**: invented weights would be false precision, and a reader would anchor on the number instead of the four facts under it. Two honesty mechanics worth keeping: CT.gov's `query.intr` is a loose text search that returns other drugs' trials, so every hit is re-checked against its own registered intervention names (including `otherNames`, where brand names live) and the drops are counted on screen; and the `fields` list is a named constant with a test asserting its contents, because omitting `HasResults` from it once made the checklist state, in a full sentence, that no trial in the programme had posted results — for a drug with sixteen that had.
- **Literature shelf** (Europe PMC). Previously declined as duplicating Google Scholar; reversed in September 2026 for one specific reason — a general search engine cannot tell you *what kind* of paper it just handed you, and Europe PMC returns MEDLINE's own publication types on every record. A primary randomised trial report, a meta-analysis, a narrative review, a conference abstract and an unreviewed preprint arrive already separated, and the composition of a result set ("4 primary papers, 15 reviews") is more informative than any single title. Two entry points: a standalone search tab, and a "what has been published about this trial" panel in the Decoder that searches the NCT number. **On the name, because it misleads:** Europe PMC is *not* a European database — its `MED` source is MEDLINE/PubMed in full, plus PMC full text, plus bioRxiv/medRxiv/Research Square preprints. Verified live: 96 of 100 records in a broad query come from MED. Adding a second general literature API alongside it would return the same MEDLINE records twice, which is why there is one.
- **Trial Glossary** (Reference Sheet). The vocabulary the decoder assumes, each term with a "why it matters" line, plus what each phase can and cannot establish.

### One fetch for every integration (`netEngine.js`, September 2026)

`resilientFetch(url, { method, headers, body, timeoutMs, label, retries })` is the only way the renderer reaches an external service; every integration's wrapper (ctgovFetch, fdaFetch, tsCtgovFetch, tsFdaFetch, europePmcFetch, cmsFetch, openTargetsQuery, fetchStudyByNctId) goes through it, and main.js's `edgar:fetch` applies the same rules in the main process. It retries what a second try can fix — no connection, a timeout (once), 408/425/429/5xx — up to twice, ~0.7s then ~1.75s with jitter, or the server's Retry-After (capped at 8s); it never retries 400/403/404, which each caller interprets itself (openFDA's 404 means "no matches"). It returns the Response, so every existing error message is unchanged. **Why:** seven of eight integrations never retried, so an intermittent 500 from openFDA or EDGAR search, or a 503 from Europe PMC, showed as a failed lookup although the same request a moment later succeeded; the eighth (EDGAR) retried everything, 404s included. A new integration must use it. `test/net_test.js` pins the rules; `npm run apihealth` (test/api_health.js) checks every live source for both reachability and extraction accuracy against hand-verified figures.

**EDGAR burn is cash used in operations** (`NetCashProvidedByUsedInOperatingActivities`, its year-to-date span divided out), not operating loss, which includes non-cash stock compensation and overstated Stoke's burn by ~12% (16 vs 18 months of runway). Operating loss is the fallback when the cash-flow tag is missing; the Cash Runway tool shows which basis it used.

### Six API lessons, all found only by calling the live service

-2. **A results analysis can register FEWER arms than it compares.** DAPA-HF (NCT03036124) files its primary hazard ratio against `groupIds: ["OG001"]` — one arm, for a two-arm comparison, with no `estimateComment` either. Printing that single arm title where "A vs B" belongs reads as though the estimate runs against nothing, or worse, as though *that* arm is the numerator. The engine passes the list through untouched; the UI refuses to print a comparison line unless both sides are named, and says the direction is not in the record.

-1. **CMS appends a footnote asterisk to some drug names, inconsistently between its own datasets.** Selexipag is `Uptravi` in the quarterly file and `Uptravi*` in the annual one, and the API filter is exact-match — so an exact query returned the recent quarters and silently dropped the entire annual history. On a launch-curve chart that leaves a mature drug's plateau sitting exactly where a new drug's ramp belongs, which reads backwards rather than merely imprecise. Names are compared with the marker stripped, and the fetch retries with `name + "*"` when the exact query finds nothing.

0. **CT.gov v2 drops a top-level field when you pass `fields` and don't ask for it.** `hasResults` lives outside `protocolSection`, and a filtered query omits it entirely — while `parseStudy` coerces the missing value to `false`. The consequence was not a blank but a confident false sentence. Any field a view reads has to be in its field list, and the list is worth asserting in a test.

1. **EDGAR full-text search returns hits in RELEVANCE order, not date order.** Asking it for one company's Form 4 filings returned 2008, 2011 and 2016 filings among the first ten of 277. Anything that means "the most recent filings of type X" must come from `data.sec.gov/submissions/CIK…json`, whose `filings.recent` arrays really are reverse-chronological — and which this file already fetches and caches for other purposes.
2. **A submissions entry's `primaryDocument` is the human-readable rendering**, e.g. `xslF345X06/ownership.xml`. The machine-readable XML is the same name with that stylesheet directory stripped.
3. **Form 4 boolean flags are written both ways.** The schema's examples use `1`/`0`; plenty of real filings use `true`/`false`. Checking only for `"1"` labelled a live filing from a Chief Financial Officer as "Other", which is not cosmetic — who was transacting is most of what an insider transaction means.

### Four more, found filling in the sample case (September 2026)

- **EDGAR full-text search names the filing type `form`** (plus `root_forms`, an array; `file_type` is the document, e.g. EX-99.1). Code reading `form_type` / `root_form` printed every catalyst filing as "?". Parsed by `parseCatalystHit()`, tested against a real hit.
- **Biotech cash is mostly marketable securities, under many XBRL tags.** Stoke files `AvailableForSaleSecuritiesDebtSecuritiesCurrent` and `…Noncurrent`; reading the first of three current tags found neither and reported $110.0M of a $354.3M balance — which "Export financials to case" would have written into the case. Current and long-term marketable debt securities now count, only when dated with the cash figure; general long-term investments do not (they can be equity stakes).
- **EDGAR's "diluted shares" is the EPS weighted average, not a fully diluted count.** A loss-making company excludes options and warrants from it as anti-dilutive. Two export paths wrote it into a case's "fully diluted shares" (Stoke: 64.5M against ~82M). They now use `edgarFullyDilutedShares()` — period-end basic plus options and warrants, treasury method at the case's price — and Company Lookup labels the EPS figure and dates every figure (`edgarAsOf`).
- **ClinicalTrials.gov knows sponsors by name, and drugs by every name they have had.** A ticker as the sponsor query found none of Stoke's three trials (Company Lookup now searches the EDGAR-registered name, suffix dropped: `sponsorNameFromEntity`), and MONARCH registers zorevunersen only as "STK-001" (Asset Program now takes several names — "zorevunersen, STK-001" — searched with OR and matched on any: `assetProgramNames`).

### Two more, found on the PepGen pass (September 2026)

- **ClinicalTrials.gov's condition search expands synonyms and abbreviations, sometimes into another disease.** "Myotonic dystrophy type 1" goes through "DM1" to T-DM1 (trastuzumab emtansine): 18 of 23 Phase 2 hits with posted results were cancer trials. Every condition search (competitor scan, Trial Explorer comps, analog effect board) now runs `filterStudiesByCondition()` — a hit must name the query's real words in its conditions, keywords, titles or MeSH terms (all of them for one or two words, half for longer queries, on stems) — and each panel counts what it dropped. A one-word query is left alone (it may be an abbreviation expanded on purpose). Ask for `Keyword`, `OfficialTitle` and `ConditionMeshTerm` in any new field list that feeds it.
- **openFDA's label section is `warnings_and_cautions`** (`warnings` on older labels). The app read `warnings_and_precautions`, which does not exist, so no label ever showed its Warnings & Precautions. API health now asserts the section.

### Two API lessons worth not relearning

Both new integrations were written against assumed API shapes and **both were wrong in ways the unit tests could not catch**, because the fixtures encoded the same wrong assumptions as the code. Only calling the live services exposed them.

1. **Open Targets v4 has moved.** `knownDrugs` no longer exists (it is `drugAndClinicalCandidates`), a clinical row's `diseases` are wrapper objects with no `name`, and stages arrive as `"PHASE_3"`. Introspect the live schema before trusting any query here.
2. **CT.gov's `paramType` is free text, not an enum.** Real values include `"Hazard Ratio (HR)"` and `"CMH ESTIMATE OF COMMON ODDS RATIO"`. It must be pattern-matched — and narrowly: anything on a transformed scale (a log hazard ratio) is refused outright, because its null value is 0 rather than 1 and mixing the two would corrupt every summary on the board.

3. **A results record's denominators are not the arms you think they are.** KEYNOTE-189 registers five adverse-event groups, three of them crossover and re-treatment cohorts — one with nine patients, one with two. Ranking events by their highest rate across all five put a 2-of-9 event at the top of a table where every visible column read 0.0%. Rank and display against the groups with the real denominators, not all of them. The same record registers ~44,000 "not completed" participants whose reason is *entering the open-label period*, and NCT04368728 the same: read as attrition that is 99.8% dropout on a trial whose real dropout was about 2%.

Corollary, learned the same way: **test a new CT.gov feature against a real mega-trial.** NCT04368728 registers 64 primary endpoints and 20 arms, which broke the decoder's rendering and made its co-primary red flag produce nonsense. No synthetic fixture would have suggested those numbers were possible.

## Deliberately not built — do not "fix" these as if they were oversights

Explicit, discussed, scope-line decisions, not gaps:
- 13F institutional holdings (different filing type from Form 4 insider transactions, which *is* built)
- Versioned snapshots of the whole case (model snapshots in the Evidence Log are dated since October 2026 — that narrow reversal only)
- Position sizing of any kind (user's decision, October 2026: investment-advice territory with no clear criterion)
- Platform/pipeline correlation for Sum-of-the-Parts
- Regulatory precedent library
- Group-sequential trial modeling
- QED/PAINS/SA-score molecular metrics (also: confirmed not available in the RDKit WASM build in use — a real technical constraint, not just a scope call)
- **Code signing / notarization.** Decided against, with reasons, not deferred. It costs $99/yr for an Apple Developer account and buys exactly one thing: removing the Gatekeeper prompt for someone who *downloads* the app. It does nothing for the user's own use — a locally built app never gets a `com.apple.quarantine` flag, which is why it already opens with no warning. This is a personal tool; paying an annual fee to smooth a one-time click for other people is not worth it. Anyone the user shares it with can still run it via the manual override in System Settings → Privacy & Security. **Do not re-raise this as a gap.** It would only become worth revisiting if Apple removed the manual override entirely, or if the app were ever distributed at scale.

If a future request seems to want one of these, say so plainly and ask before building — don't silently reopen a closed scope decision.

## Known limitations — real gaps, not modesty

- **The original 38-check core-engine regression suite from the earliest build sessions did not survive a sandbox reset** and was never reconstructed as such — but treat this as closed, not open: `test/math_verification.js` is not a "leaner replacement," it now independently verifies 1,589 hand-derived checks (the suite prints the current count) (including a year-by-year rebuild of the PepGen case) across the full engine (revenue build, cost chain, capital structure, every trial-statistics formula, chart axis logic, storage accounting), each checked against a value worked out longhand in its own comment rather than recorded from the app's own output. Read `test/README.md` for the exact scope/rules of what this suite does and doesn't claim.
- **Accessibility is checked automatically, not audited by a person.** `test/packaged/ui_audit.js` covers contrast, text size, target size, control labels and chart names across every view, both themes and two widths, and (September 2026) keyboard and screen-reader basics: nothing that looks clickable is mouse-only, a real Tab walk through every view finds a visible focus ring at every stop, and every interactive node in Chromium's accessibility tree has a name. All zero findings. Not done: a hands-on VoiceOver session, and reading order / announcement quality — the tree says every control *has* a name, not that every name reads well. Block-level clickable rows use `buttonLikeProps()` (helpers.js) rather than a bare `onClick` div; that pattern had left every Workspace input card and the case list unreachable by keyboard.

## Coding conventions actually followed throughout this build

- **Hand-verify new math against real, independently-computed numbers before trusting it** — not just "does it run without crashing." This caught multiple real bugs throughout the project (a units error inflating dilution by ~1,000,000x, a PoS-composition bug silently understating Bear-case burn, a fractional-launch-year bug silently zeroing cash flows). Assume the same discipline is expected of any new numeric feature.
- **Optional/possibly-missing fields are read defensively**, via a shared normalizer function where one exists (e.g. `getRevenueBuild()` in `engine.js`), not scattered inline `|| {}` guards. A real crash (missing `revenueBuild` white-screening the entire app) came from exactly this pattern being inconsistent — some call sites guarded, one wasn't.
- **Never silently swallow a failure a user would care about.** `saveCustomComps()` used to catch-and-ignore a failed `localStorage` write; fixed to return success/failure so callers can warn the user, since data was being silently lost. Apply the same standard to new persistence paths.
- - **Screenshots of the Electron window: use `captureBeyondViewport`.** CDP's plain `Page.captureScreenshot` **hangs indefinitely** when the app window is on another macOS Space or is otherwise occluded — Chromium's compositor never produces a frame. `fromSurface: false` does not help. `Page.captureScreenshot({ captureBeyondViewport: true, clip: {...} })` renders off the compositor path and works regardless. The computer-use `app_screenshot` tool can also capture an off-Space window, but **cannot click it** (`app_bring_to_current_space` fails outright if the user's current Space is a full-screen app), so CDP with `captureBeyondViewport` is the reliable path for any check that needs interaction.
- **`test/packaged/case_fill.js` types a whole case into the packaged app** from a plan (`test/packaged/fixtures/pepgen_fill_inputs.json` is PepGen's: 167 actions including the Evidence Log, calibration and partnership forms, 101 stored values checked; `expectNow` checks a value mid-plan, `clickLabel` presses a button by aria-label) — fields found by label, typed one key at a time via CDP `Input.insertText`, then every stored value compared with what was typed (units included). Setting a value in one go cannot see a field that rewrites itself between keystrokes; this found MillionsField storing $117.238M as $11.7B. Run it after changing any input component.
- **`test/packaged/packaged_check.js` is how to verify inside the packaged binary** (`cd test && npm run packaged -- --mode=offline|reopen|live`). It runs the installed app's own main.js/preload under the project's Electron with only the save dialog replaced, so IPC, CSP, printToPDF and the offscreen section renderer are real. Use it after any change to export, the report, the CSP or main.js — it found three defects in September 2026 that the whole jsdom suite could not see. `npm run canary` does the same job for CT.gov schema drift.
- **`npm run lint` (from `test/`) must stay clean.** ESLint over the concatenated source (see `test/lint.js`): undefined names, unused code including top-level functions, unreachable code. It was brought to zero in September 2026 — the cleanup removed a dead chart-PDF IPC channel, an old section-nav component, dead CSS, and found a real bug (the Portfolio PoS scatter referred to a diagonal it never drew). Repeated inline style objects in the React views now come from `UI` in helpers.js (`style: UI.caption`, or `{ ...UI.caption, marginTop: 8 }`); use it rather than pasting the object again.
- **`test/packaged/button_sweep.js` presses every ordinary button in every view** of the packaged app on a finished sample case (`--sample=pepgen|stoke`), rebuilding the view before each press, and fails on a crashed view or a console error; destructive buttons, export menus (the export sweep's job) and native dialogs are left alone. **It runs four copies of the app in parallel by default** (`--parallel=N`; each takes every Nth press) and has a time limit on every call into the page (`--timeout`, 20s) — a press that does not answer is reported by name and the page reloaded — plus a run-wide cap (`--max-minutes`, 30). Before October 2026 it had neither, and a run that hit one unanswered call sat for five hours without finishing; now a full sweep takes about 9 minutes per sample (787 / 770 presses, 0 problems) and prints each view's time. The window's timers are never throttled (`disable-background-timer-throttling` and friends), since a hidden window otherwise runs its timers once a minute.
- **Monte Carlo checks in `math_verification.js` run from a fixed seed** where a result is compared with another (mulberry32 in place of `Math.random`, restored after; see the delayed-separation section), and any live-randomness tolerance is at least four standard errors with the arithmetic in its comment. Two were two to three SEs wide and failed by chance (October 2026 audit).
- **`button_sweep.js --userdata=<dir> --case="<name>"`** sweeps a copy of an existing profile (each parallel copy gets its own copy; the original is never written) — how cases saved before newer fields existed get tested.
- **`case_fill.js --userdata=<dir> --case="<name>"`** drives an existing case on a given profile (the user's real data, backed up first) without changing the theme; `editEvidence` / `editCalibration` steps update entries in place through their Edit buttons.
- **UI checks: `test/packaged/ui_audit.js`** (`--sample=stoke|pepgen` audits a fully filled case — the blank default case never shows the readout scenarios, the partnership panel or the biomarker helper, and that is where the last findings were) walks every view and tab of the packaged app in dark and light at 1470px, and dark at 900px, and reports export buttons overlapping their section's content, a scroll box drawing a scrollbar for 1–4px of overflow (the Workspace tab row did, October 2026), text contrast below WCAG AA (opacity compounded, background walked to the first opaque ancestor), text under 10px (sub/superscripts exempt), clipped text, click targets under 24x24, unnamed buttons, unlabelled inputs, charts with no accessible name, chart text under 8px, sideways scrolling and console errors, and saves a full-page screenshot of every view. Rerun it after any styling change and **look at the screenshots** — it found none of the chart bugs below; eyes did. Conventions it enforces: body text never under 10px; export rows are quiet by styling (grey text, hairline border), never by opacity; every button at least 26px tall; every input carries an `aria-label` when its visible label is not a `<label>` around it.
- **Plain-English readings (`Explain`, helpers.js).** Sixteen results carry one bold verdict and one sentence saying what *this* result means (price vs Bear/Base/Bull, Monte Carlo vs price, cash-flow payback, SOTP, both risk waterfalls, the tornado and price grid, binary event, M&A premium, forward runway, and the Simulation CI, p-value, single-arm, assurance and peak-sales tools; `explainNode()` is the plain-DOM twin). Each `read*()` function is pure, returns null when it has nothing honest to say, never computes a new number, and is pinned by hand-worked checks in `math_verification.js`. They say which way a result sits, never which way is good when the tool cannot know (an interval against 1 does not know if the endpoint is a benefit or a harm). The static "New here?" notes explain how a tool works; a reading explains the result — keep the two separate.
- **Chart axes use round numbers.** `niceAxisTicks()` (chart.js, React side) and `niceTicks()` (ts_chart.js, Simulation side) pick steps of 1/2/2.5/5×10ⁿ, so zero is always a labelled gridline when the axis spans it. Don't grid a chart at fractions of its raw range — that labelled a profit/loss line "$1M". Bars for a quantity with a natural full scale (a probability) are drawn against that scale, not against the largest value shown; bars that can be negative run from zero on a shared axis.
- **Verify inside the actual packaged binary before considering something delivered** — not just in source, not just in a test harness. Every feature in this project was confirmed present via `grep`/byte-search inside the built `.app`'s `app.asar` before being called done.
- Copyright/citation discipline (paraphrase over quoting, one short quote per source max) governed research done *during* chat-based development for comps data — not directly relevant to Claude Code's own work, but explains why comps entries are written the way they are (paraphrased deal terms, not quoted press-release language).

# RxNPV — External Model Suggestions: Final Synthesis

Four models consulted (A, B, C, D) against the `RxNPV_Feature_Overview.md` context document. This is a full rebuild, not an append — the overlap across all four was extensive enough that a clean, consolidated version is more useful than a fourth appended section. Every technical claim that could be checked against the actual code was checked, not assumed; corrections are called out explicitly where a model's premise turned out to be wrong or only partially right.

**Verdict key:** ✅ Build it · 🟡 Worth doing, lower priority · 🔍 Needs real scoping first · ⚠️ Tension with guardrails · ❌ Don't build · ✔️ Already exists

## Cross-model consensus — where independent models converged

This is the most useful signal from consulting four separately: when models that never saw each other's output land on the same idea independently, that's real evidence of a genuine gap, not one model's idiosyncratic take.

- **Partnered-economics valuation mode** (C, D) — both independently identified the same real hole: both existing valuation methods assume the company owns 100% of the asset through commercialization. D's framing is the more precise of the two — a third mode risk-adjusting an upfront payment to signing PoS, each milestone to its own gate's cumulative PoS, and a royalty rate on the existing peak-sales build. Pairs naturally with Model A's licensing-comps-database idea, using the exact architecture the M&A and Peak Sales comps already use.
- **Time-aware / dilution-path financing** (C, D) — same core idea, connecting inputs the engine already computes (R&D-to-launch cost, cash runway) into a funding-gap-driven share-count projection at each future point. D's framing is sharp: this fixes "the single most common retail valuation error" — rNPV on today's share count, ignoring that getting to launch usually costs more dilution than the current cap table.
- **Reverse-solve beyond PoS** (C, D) — both spotted the same natural extension of the already-built, already-verified Implied PoS solver: parameterize it to solve for implied peak sales, implied market share, or implied launch year instead, one at a time. Genuinely low-risk since the reverse-solving machinery already exists and works.
- **Portfolio-level cross-case view** (A, D) — same idea, aggregate dashboard across every case tracked, sliced by fair-value-vs-price, catalyst timing, and risk exposure.
- **Structured red-flag / consistency checks** (A, D, and C's dossier red-flag list) — three-way convergence, though from different angles: A and D both propose portfolio/financing-oriented flags (concentration, financing overhang, insider selling); C's version is clinical-trial-specific (small/unrepresentative population, open-label bias, multiplicity risk). These are complementary dimensions of the same feature, not redundant.
- **Evidence/citation tracking for assumptions** (A, C's ledger, C's dossier) — three converging proposals at increasing depth: A's general evidence log, C's confidence-level-and-snapshot-diff refinement, C's clinical-trial-specific dossier. Same underlying need at three levels of granularity.
- **Versioned snapshots** (A, C) — same idea; C adds attributing a value change to a specific driver category (data vs. commercial assumption vs. PoS vs. financing), which meaningfully sharpens A's original framing.
- **Platform/pipeline correlation for SOTP** (C, D) — both independently flagged that a multi-program SOTP can overstate diversification when programs share a platform, biology, or biomarker premise, and both frame it as an optional overlay on the existing risk waterfall, not a forced assumption.
- **Cash tax / NOL treatment** (C, D) — both suggest it, both independently rank it low priority themselves.
- **Competitor timeline visualization** (B, C) — same idea (Gantt-style layering of own and competitor trial readouts), B naming the chart type, C extending it to include exclusivity events.
- **Avoid market-data/price-feed features** (A's own flagged tension, D's explicit closing guidance) — D independently reaches the same conclusion I'd already flagged about Model A's event-study suggestion, from the opposite direction: real-time price feeds, portfolio accounting, and options analytics don't fit the free/local/methodology-transparent architecture. Worth treating this as settled, not just my own caution.

## Corrections — where a model's technical premise didn't hold up

Checked against the actual code or package contents, not taken at face value:

- **SEC XBRL for cash/debt/shares (B):** ✔️ already built — confirmed in a prior round, restated here for completeness. `edgarEngine.js` already pulls structured XBRL tags directly.
- **Gross-to-net / launch-access modeling (C):** the framing implies this is untouched. It's not — pricing already uses an explicit "US annual price per patient (ASP basis)" input, a simplified net-of-rebates proxy, not gross list/WAC. The real gap is narrower than presented: going from one net-ish number to a full WAC → gross-to-net% → ramp-to-steady-state decomposition specifically for the early-launch period, not building net pricing from nothing.
- **Multi-dose PK "superposition" (D):** the framing implies this needs building from scratch. The engine already numerically simulates repeat dosing — `tau` (dosing interval) and `numDoses` are real, working config inputs, and accumulation is already visible in the resulting concentration-time chart. The real gap is narrower: making steady-state Cmax/Cmin and an explicit accumulation-ratio number a *stated* output, not something you'd have to eyeball off the chart yourself.
- **QED / PAINS / SA-score "near-zero cost since RDKit is already wrapped" (D):** checked directly against the actual RDKit.js WASM package's type definitions — genuinely not present. The available API surface covers molecular manipulation, format conversion, fingerprinting, and substructure matching; there's no QED function, no FilterCatalog, no synthetic-accessibility scorer anywhere in it. These are real features of full Python RDKit, but the specific minimal WASM build this app uses doesn't expose them. Implementing them would mean writing the scoring logic in JS using the raw descriptors that *are* available (QED is a published, reproducible formula, so this is realistic) — a genuine, scoped build, not a function call.

- **Launch monitor** (C) — 🟡 Worth doing for anyone tracking a commercial-stage name specifically — quarterly actual-vs-model tracking post-approval. Complementary to the Calibration Log (that's pre-catalyst PoS scoring; this is post-launch commercial-execution scoring), not the same feature.
- **Thesis journal** (D) — 🟡 Worth doing, lighter-weight and more narrative than the structured Evidence Log — a different granularity of the same underlying need, not a duplicate.
- **Endpoint-specific templates** (A) — 🟡 Worth doing, low-lift.

### Clinical, regulatory, and scientific depth
- **Evidence-to-assumption ledger / program evidence dossier** (A, C, C) — ✅ Build it. The most-reinforced idea in this entire review across three separate proposals at increasing depth. Scope the general evidence log first (source, date, confidence, thesis per key input), then let the clinical-trial-specific depth (design, endpoint hierarchy, red-flag checklist) be an optional deeper layer within a program's dossier, not a second system.
- **Europe PMC literature integration** (B) — 🟡 Worth doing as one of several source types feeding the evidence log above, not a standalone tool.
- **Platform/pipeline correlation for SOTP** (C, D) — ✅ Build it. Methodologically real — same-platform programs don't fail independently — and both models scope it correctly as an optional overlay, never a forced assumption.
- **Receptor occupancy bridge for PK/PD** (B) — ✅ Build it. Genuine mechanistic improvement, low-risk addition to the already-validated Emax function.
- **Group-sequential / interim-analysis modeling** (D) — 🟡 Worth doing. Real statistical depth for the Trial Outcome simulator — many pivotal designs have interim looks that change both the probability and timing of a positive readout.
- **Multi-dose steady-state metrics as explicit output** (D) — 🟡 Worth doing, smaller than framed per the correction above — expose what the engine already computes, don't rebuild it.
- **QED / PAINS / SA-score** (D) — 🔍 Needs real scoping, not near-zero cost per the correction above. Worth doing eventually since QED specifically is a reproducible formula over descriptors already extracted, but budget it as a real build.
- **CT.gov snapshot-and-diff** (D) — ✅ Built. New standalone "Trial Watch" tab, not tied to any case — a real program can have several relevant trials, and forcing a one-trial-per-program data model onto that would have been the wrong shape. Each check saves a snapshot (status, phase, enrollment, primary completion date, primary endpoint text) keyed by NCT ID and diffs it against whatever was saved last time; the first check on any trial just sets the baseline, correctly shown as "nothing to compare yet," not an error. Required extending the CT.gov integration's parseStudy with primaryOutcomes (the actual endpoint text) and a new direct single-study lookup (`GET /studies/{nctId}`, confirmed via the official field reference before building on it, not guessed) — the app previously only ever searched by criteria, never fetched one specific trial directly. A watchlist of every previously-checked trial persists across sessions with re-check and forget actions per entry. Hand-verified the diff logic catches all four tracked change types at once (status, enrollment, completion date, and endpoint swaps shown as added/removed rather than a single before/after string, since a list changing isn't the same kind of event as a single value changing), confirms zero changes on genuinely unchanged data, and confirmed error handling for invalid NCT ID formats, a real 404, and a network failure.
- **FAERS disproportionality (ROR/PRR)** (D) — 🟡 Worth doing, needs careful, explicit caveat labeling (not incidence, quarterly lag) given the app's existing discipline around not overstating what a number means.
- **Insider transactions (Form 4)** (D) — ✅ Built. 13F institutional holdings is a genuinely different filing type and stayed out of scope — this covers Form 4 insider buys/sells specifically, the "classic retail signal" half of the original suggestion. Turned out to need real research to get right, not the quick add "EDGAR's already integrated" first suggested: Form 4s are filed under the *insider's* CIK, not the issuer's, so the company's own submissions endpoint doesn't list them — discovery goes through the same full-text search (`efts.sec.gov`, `ciks=` filter) the catalyst calendar already uses, then each matching filing's actual ownership XML gets fetched and parsed for the structured transaction data (shares, price, transaction code) that search-result metadata alone doesn't carry. The XML parser was hand-verified against a real, live SEC Form 4 document fetched directly from sec.gov — every field (issuer, owner, role, shares, price, transaction code) confirmed to match the actual filing exactly, not a synthetic example. The main-process IPC bridge already gracefully handled non-JSON responses without any changes needed there; only a renderer-side function to actually read that fallback text field was missing, for XML instead of JSON.
- **13F institutional holdings widget** — still open, genuinely separate from the above (quarterly institutional positions, not insider transactions — a different filing type, different signal, different discovery mechanism).
- **Advisory-committee dates in Catalyst Calendar** (D) — 🟡 Worth doing, small, admittedly semi-manual since there's no clean API for this specifically.
- **Regulatory-risk overlay tags** (A) — 🔍 Good instinct, tighter scope needed. Keep visible and human-actionable; no automatic linkage to discount rate or scenario weights, not even opt-in — that kind of soft mechanical link tends to drift from optional to unexamined-default over time.
- **Cash tax / NOL schedule** (C, D) — 🟡 Worth doing, both models rank it low themselves — matters once a name approaches sustained profitability, little relevance for typical Phase 1–2 names.

### Flagged tensions with existing guardrails
- **Event-study price-history hooks** (A) — ⚠️ Real tension, now reinforced from the opposite direction by D's explicit caution against market-infrastructure-flavored features. Every existing integration is an official government API; a free price feed is a meaningfully murkier category, closer in risk profile to the already-declined Orange Book and ADMETlab integrations than to anything currently in the app.
- **Position-sizing helper** (A) — ❌ Don't build. Functionally investment-advice territory regardless of "non-prescriptive" framing, cuts against the no-recommendations discipline the whole app is built around.

## The committed plan

Not a loose ranking — this is the actual sequencing, with the reasoning for why things are ordered this way, not just what they are.

### Short term — first sprint, in order — ✅ COMPLETE
1. **Evidence Log (general version)** — ✅ Built. Per-program section, freeform-labeled entries (not bound to a specific field name), classification/confidence dropdowns matching the Biotech Agent's exact vocabulary.
2. **Structured red-flag checks** — ✅ Built. Five checks (PoS override, COGS, R&D timeline, peak share, cash runway vs. launch timing), all auditing data already in the app. One real bug found and fixed along the way: an untouched new case was false-flagging on its unset ($0-defaulting) cash field.
3. **Reverse-solve beyond PoS** — ✅ Built. Solves for implied peak revenue, peak market share, or launch timing, reusing the Implied PoS solver's binary-search pattern. Round-trip verified for all three. Surfaced and fixed a real, previously-latent core-engine bug along the way: fractional launch years produced non-integer array indices, silently zeroing out cash flows for years landing on the fraction — fixed at the single source function so it protects every downstream consumer.
4. **Calibration log, started now despite being small** — ✅ Built. Records a PoS prediction (yours and the market's) before a catalyst, an outcome after, and computes Brier scores for both — verified against hand-calculated reference values.
5. **Receptor occupancy bridge** — ✅ Built. Optional K_D input bridges concentration to target engagement before the Emax curve; verified the Hill-Langmuir equation's exact-50%-at-C=K_D property holds through the full UI pipeline.

None of this sprint touched the core valuation engine's methodology — the one exception was the launch-year bug fix, which corrected existing, already-shipped logic rather than adding anything new to it.

### The two big ones — sequenced, not simultaneous
6. **Dilution-path financing** — ✅ Built. Projects when cash would run out (reusing the same cash-flow machinery as the runway calculator) and models a raise there — at current price less an assumed discount, sized to restore a maintained buffer plus cover a set number of forward months — repeated through to launch, plus optional continuous SBC share creep. An alternative to the single future-raise overlay, not additive with it. Only affects the diluted-share divisor, never adds raised cash to net cash (would have double-counted the same R&D spend already reflected as negative cash flow in the NPV — verified this distinction explicitly). Three real bugs found and fixed during verification, not before it: a units error inflating cash balances by ~1,000,000x (traced to `MillionsField`'s actual raw-dollar storage convention, which I'd misread); a scenario-composition bug where forcing "unrisked" R&D cost didn't reliably reach exactly 100% when a Bear/Bull scenario's own PoS multiplier was also in play, silently understating Bear's burn; and a missing-price edge case where a blank current price fell through to a $0.01/share floor and produced billions of shares from a normal-sized raise, fixed by removing the floor so raising is correctly skipped without a real price. Differentiation across Bear/Base/Bull confirmed genuine with an extreme test case (10% vs. 500% revenue), though realistic Bear/Bull multipliers don't always cross a raise threshold differently in every case — that's an honest property of the model, not a flaw.

7. **Partnered-economics mode** — ✅ Built (the comps database piece below is still open). Built as an optional overlay on Quick/Detailed, not a third peer mode — Quick and Detailed both answer "what's total peak revenue," partnership answers "how much of that flows to the company," which is a different axis, not a third way of building the same number. Royalty substitutes the partnered territory's revenue rather than adding to it (verified this doesn't double-count against Detailed mode's own ex-US modeling — Quick mode has no US/ex-US split at all, so only whole-asset partnership applies there). Upfront is a direct undiscounted add; each milestone is risk-adjusted to its own gate's cumulative PoS and discounted from its own expected timing, not lumped in with launch — verified against hand-calculated values to the cent, including the edge case of a milestone tied to an already-passed phase (correctly treated as certain, undiscounted). Cost-sharing reduces the company's own R&D burden by the partnered %. All of this reuses the exact machinery already governing PRV (same risk-adjustment, same discounting, same "self-contained additive contribution to equity value" pattern), so it's one more instance of an established shape rather than new architecture.
   - **Licensing/royalty comps database — ✅ Built.** 8 deals, each multi-source-verified against the companies' own press releases and, wherever available, primary SEC filings (8-K, 10-K, 10-Q, 6-K) rather than a third-party deal tracker alone — several other candidates found during research had inconsistent figures across sources and were left out rather than resolved by guessing. Spans $6.5M to $1.35B upfronts and 5 therapeutic areas, including one very recent (January 2026) mega-deal for current relevance. Royalty ranges are only shown where a specific numeric range was actually disclosed — several real deals only ever say "tiered royalties" or unqualified "double-digit," and those are stored as genuinely unknown (null) rather than filled in with an assumed figure; a 50/50 profit-share deal (AstraZeneca/Daiichi Sankyo) is explicitly labeled as not royalty-based at all, rather than forced into the same royalty fields as the others. Exports directly into a program's Partnership Economics overlay (upfront and royalty midpoint), and correctly leaves an existing royalty rate untouched when exporting a null-royalty deal rather than silently blanking it — verified this specific edge case explicitly. Custom-add/edit/delete included, reusing the exact same generic form component and localStorage pattern already proven for the M&A and Peak Sales comps, per the explicit request to support custom entries here too.
   - Two real bugs surfaced during testing, both traced to my own test scripts' DOM traversal, not the app: one where a broad ancestor-matching selector caused an export test to grab the wrong deal's values (root-caused via an isolated, DOM-free unit test of the export math, which confirmed the calculation itself was exactly correct before touching the UI test again); another where `.textContent` equality matched a wrapper div instead of its leaf label child, since an `<input>` contributes no text of its own. Both fully diagnosed and fixed before treating the feature as verified.

### Medium term — genuinely better for waiting, not just deferred
8. **Portfolio view** — ✅ Built, right on schedule per its own stated reasoning: the prerequisites (evidence-logged assumptions, realistic runway via dilution-path financing) were genuinely in place by the time this got built. A new top-level view aggregating every saved case's already-computed valuation — summary table (price, fair value, upside, runway, modeled and implied PoS), a PoS-dispersion ranking, a cash-runway ranking (shortest first, under 12 months flagged), and a modeled-vs-implied PoS scatter reusing the existing chart component. No new data source anywhere — every number comes from re-running each case's own existing valuation/runway/PoS functions, nothing case-specific gets written back. A case with incomplete or broken inputs is included with a visible error flag rather than silently dropped or crashing the rest of the portfolio — verified this explicitly with a deliberately malformed case. Backward-compatible with cases saved before any feature built this whole session existed, confirmed with a case missing every one of them at once.
9. **Versioned snapshots** — same "start early, compounds over time" logic as the calibration log, just a bit more effort to build.
10. **Platform/pipeline correlation for SOTP**, **regulatory precedent library**, **group-sequential trial modeling**, **13F institutional holdings** — all genuinely good, none urgent. (Insider/Form 4 transactions and CT.gov snapshot-and-diff, previously listed here, are now built — see above.)

### Capstone — unchanged
11. **Full-case Monte Carlo rNPV** — ✅ Built. The capstone, built last exactly as planned. 3,000 trials per run, sampling PoS, peak share, and discount rate continuously from triangular distributions anchored to each case's own Bear/Base/Bull bounds (respecting any per-case override) instead of only three fixed points — reuses `computeCaseValuation` itself unchanged for every trial, plus the same triangular-sampling and Pearson-correlation functions the Peak Sales Monte Carlo in Simulation already uses and has been verified against. No new valuation methodology anywhere in it. One genuine, worthwhile discovery during verification: the simulated median doesn't exactly match the Base-case point estimate, and I didn't wave that away — traced it to a real, expected property (discounting is mathematically non-linear, so uncertainty in the discount rate alone pulls the distribution's center measurably below the naive point estimate), confirmed it precisely by isolating each varying input individually, and it's now stated plainly in the UI rather than left as a confusing discrepancy. Extracted the Bear/Bull override-resolution logic out of the UI layer into a shared function during this build, since the Monte Carlo needed the exact same resolution the existing scenario comparison already had — verified the refactor byte-identical to the original before building anything on top of it.

### Post-capstone polish — self-identified, not from the original four-model suggestion set
After the capstone, did an honest audit of the Simulation section (all 6 tabs, read the actual implementation rather than go by tab names) and of cross-tool connectivity generally, rather than manufacture busywork. Conclusion: Simulation's 6 tabs already cover every real dimension of uncertainty worth modeling — the only genuine gap found was connectivity, not breadth, since these tools had zero export/cross-reference links despite the Tools tab's comps having them throughout. Three concrete items came out of that audit, all ✅ built:
- **Peak Sales Monte Carlo → case export.** The one significant piece of new plumbing, since TrialSim's Peak Sales tab is vanilla-DOM code with no React access, while `cases`/`updateCase` live in React state. Built a standard bridge (`SimulationView` republishes `cases`/`updateCase` onto a plain `window.pdcfSimBridge` object on every render; TrialSim's own export button reads/calls it directly) rather than restructure either side. Exports only the P50/median — deliberately not P10/P90 as separate options, since offering those would suggest a precision a single click doesn't have. Same explicit, one-click pattern as the Tools tab's comps, never automatic. Verified the trickiest part specifically: switching between two cases with different-named programs correctly rebuilds the program dropdown and the export correctly targets whichever case/program is currently selected, not a stale reference to the first one loaded.
- **Company Lookup → Trial Watch link.** A "Watch this trial" link next to each trial in a company's pipeline results, pre-fills and auto-runs the check on arrival rather than making the user re-type the NCT ID they just clicked.
- **Partnership Economics → Licensing Comps link.** Only shown once Partnership is actually enabled (not before), takes the user straight to the Licensing Comps tab to sanity-check the royalty/upfront terms they're entering. Required a genuine cross-view navigation mechanism (App owns the "which tab to land on" request, since Partnership lives in Workspace and Licensing Comps lives in Tools) — built once, at the App level, and reused for both this and the Trial Watch link where the routing was simpler (both siblings within Tools, so no App-level routing needed for that one specifically).

## Rename to RxNPV, then a user-driven bug-fix and restructure pass

The above tracker covers the original four-model external-suggestions review and its build-out. What follows is a separate, later engagement: renamed the app, then worked through an itemized list of issues the user found using it for real trials, prioritized lowest-impact-first per their instruction, executing autonomously through each phase per their standing "just continue through your list" direction, with a comprehensive bug check reserved for the end.

### Phase 0 — Rename to RxNPV
✅ Done. Renamed throughout: source, build output (`electron/rxnpv.html`), package identity (`com.rxnpv.app`), window title, export filenames, EDGAR user-agent string, docs filenames (this file included). The one real risk — Electron's `userData` directory is derived from the app name, so a bare rename would silently orphan every existing case, custom comp, and calibration log already saved under the old profile — was closed with a startup migration that only fires when the new profile has no committed data yet and the old one does (checked via presence of a real `.ldb` file, not mere directory existence — Electron itself pre-creates an empty profile before any app code runs, which broke the first, naive version of this guard). Verified end-to-end: the real "Stok Therapeutics" case migrates and loads correctly, and every live integration (EDGAR, CT.gov, RDKit, desktop IPC) still functions post-rename with zero console errors. Caught and fixed a genuinely dangerous side effect along the way: `test/setup.js` still pointed at the old build filename, so a full regression run had silently "passed" against a stale pre-rename fixture instead of failing loudly — fixed and confirmed a genuine pass from a fresh build afterward.

### Phase 1 — Bug fixes from first real-trial usage
✅ Done. Four items, all from direct usage rather than a suggestions review:
- **Delete confirmation.** Case and program deletion previously fired immediately on click with no undo. Added a generic, reusable `ConfirmDialog` (Escape/backdrop-click to cancel), wired to both delete paths. Verified Cancel is a true no-op and Confirm performs exactly one deletion — not just that a dialog visually appears.
- **"Jump to" workspace navigation**, reported as "buggy and hit or miss." Root cause was two compounding issues, not one: an `IntersectionObserver`-based scroll-spy whose rootMargin band could miss short sections or sections at the very end of a scrollable page, and a "click sets active state, then scrolls" pattern racing against that same live observer during the scroll animation. Replaced with direct scroll-position calculation plus an explicit "currently auto-scrolling" flag that suppresses the observer until the scroll genuinely settles. Verified by sampling the highlighted nav state throughout a real scroll animation, not just checking the end state.
- **Light-mode color contrast**, reported as "jarring... some colors too dark while text is too light." Computed WCAG contrast (relative luminance, not eyeballed) for every theme token against all four light-mode background tokens and found 9 real failures — an earlier contrast pass had only checked one background token, missing that the header bar's background is darker than what was checked. Fixed with small hue-preserving darkenings. Fixing that surfaced a second, architecturally distinct bug: darkening a token for its TEXT role broke its existing use as a solid BUTTON FILL in the opposite direction (near-black text on a now-too-dark teal fill). Introduced separate `--teal-fill`/`--red-fill` tokens to decouple the two roles, which also caught a previously unflagged dark-mode failure in the storage-full warning banner that the normal navigation sweep never exercises. Audit went from 9 failures to 0 across both themes.
- **PoS scenario-card label**, reported as confusing "no base case POS modifier" — the user's read was that Bear/Base/Bull showed a probability multiplier rather than an actual probability of trial success, and correctly flagged that PoS "cannot possibly be over 100%." The underlying math was already correct and already properly clamped 0–100% (confirmed by reading the clamp site directly) — this was purely a mislabeled UI value. Fixed to show the program's actual resulting PoS for a single-program case (hand-verified against the known Oncology Phase 2 reference case: 6.1% / 8.7% / 11.3% for Bear/Base/Bull), falling back to the "% of modeled PoS" framing only for multi-program cases where a single number wouldn't mean anything.

### Phase 2 — Restructure: cut Chemistry, consolidate stats tools, relocate live-research tools
✅ Done. Simulation's original 10 tabs read as sprawl rather than depth, and Chemistry specifically was judged (by the user, after being asked directly) not worth keeping — "probably a pointless feature." ## Phase 16 — Quick vs. Detailed: mode separation without losing capability

✅ Done. The user's hypothesis was that the app had two valuation modes — a "napkin" simple-multiple and an institutional book-based DCF — and wanted separation so double-counting and irrelevant inputs were minimised.

**The hypothesis was right in spirit, but the app wasn't built that way.** There are two *independent* toggles at *different scopes*: `revenueMode` per program (Quick/Full — how peak revenue is derived) and `valuationMethod` per case (DCF/Simple Multiple — how peak revenue is valued). The user's mental model is the diagonal of that 2×2.

**Checked the double-counting concern against outside practice before acting, and the app was already right.** Applying PoS *and* discounting on top of a comp multiple is standard, not double-counting; the real risk is combining a probability adjustment with a risk-loaded discount rate, and `data.js` already carries the source's explicit note that its 15–20% range is "compatible with independently risk-adjusting the cash flows." Nothing to fix there.

**The irrelevant-input problem was real and larger than expected.** Read directly from `computeSimpleMultipleValuation` rather than assumed: in Simple Multiple mode the engine reads revenue, years-to-peak, R&D *timeline*, PoS, capital structure, financing, discount rate and the multiple — and reads **nothing** from cost structure, R&D *cost*, corporate G&A, terminal value, or cash tax. All of those were still shown and fully editable. You could tune COGS to 22% in a mode that never looked at it.

**Rejected collapsing to a strict two-mode switch, even after the user confirmed existing cases were irrelevant.** The migration concern was never the real argument. Both off-diagonal combinations are genuine workflows: a trusted consensus peak run through proper cost/timing modelling (Quick + DCF), and a bottoms-up epidemiology build valued off comps rather than modelled costs (Full + Multiple). A strict either/or would delete both.

**What was built instead:**
- **Mode presets** — one-click "Napkin" (typed peak × multiple) and "Full model" (epi build + bottoms-up DCF) that set both axes together, with a "Custom" state that names which hybrid you're in. The mental model becomes the default path without forbidding the other two.
- **Precise input gating**, driven by a single `VALUATION_METHOD_USAGE` table so the UI can't drift from the engine. Cost structure, terminal value and cash tax are hidden in Simple Multiple mode with a note saying what to switch to. R&D is deliberately *not* hidden — its timeline is live (it sets the discount horizon) while its costs are not, so the section stays with the distinction stated.
- **Stage-aware multiple guidance** — 5 of the 7 precedents are post-approval acquisitions, so those multiples price an asset with no clinical risk left. Applying one to a pre-approval program and then risk-adjusting is the correct composition, but a raw post-approval multiple is the wrong *starting point*. The panel now says so at the point of choosing, citing the 1–2× (Phase 2) and 3–5× (Phase 3) unadjusted rules of thumb against the 7.8× precedent median, and explains why the default is 3×.

Verified live in both directions: the Full-model preset restores cost structure, terminal value and tax; the Napkin preset hides all three, keeps the R&D timeline with its cost caveat, and surfaces the stage warning. 431 math checks, full suite clean.

## Phase 17 — The results reader: what the trial actually reported

✅ Done. The biggest remaining hole in the app, identified while writing `RxNPV_Feature_Map.md`: the single most important moment for an investor is the readout, and until now the app's answer to it was a hyperlink. `ctgovEngine.js` parsed the protocol and deliberately stopped at `hasResults: true` — the right call when nothing here could read a results section safely. The analog effect-size board changed that; it already reads the same schema, narrowly and with stated denominators, and this extends exactly that discipline.

New module `src/trialResults.js` (pure, no network, no DOM), folded into the **Trial Decoder** rather than given a tab of its own — same input, and putting it below the design cards makes the before/after framing explicit rather than optional. It costs no extra API call: CT.gov's single-study endpoint already returns `resultsSection` in the response the decoder was fetching anyway, so `fetchStudyByNctId()` now returns both. The results are deliberately *not* folded into `parseStudy()`, because that shape is what the Trial Watch persists to `localStorage` and a snapshot has no business carrying a 259-row adverse-event table.

**Three panels.** *Outcomes* — the registered endpoints with their per-arm values and the sponsor's own registered analysis: effect estimate, confidence interval, p-value, statistical method, and whether the comparison was **superiority or non-inferiority**, surfaced rather than buried because reading a non-inferiority result as a superiority claim is one of the most common ways a press release gets over-read. *Participant flow* — who finished and who left, by arm; differential dropout is the single most important thing the decoder structurally cannot see before results exist. *Adverse events* — for an unapproved drug this is the only real safety data that exists anywhere, since FAERS has no denominator and a label does not exist yet.

**The honesty rules, which are the whole reason this was safe to build:**

- **Nothing infers which arm is the drug.** CT.gov does not state it reliably, so groups are reported under the sponsor's own titles and every difference is signed and explained, never editorialised as good or bad.
- **A measure reported across strata or categories is never collapsed into one number.** Real records go up to 56 classes. Only a single-class, single-category measure is a plain "this arm got this number"; anything else says how it was reported and points at the record.
- **Deaths are never counted as dropout**, and neither is moving into an open-label extension.
- **A reason the sponsor never registered reads as "not registered", not 0.0%.** KEYNOTE-189 files no "Adverse Event" withdrawal row at all; printing 0.0% would turn a gap in the record into a clean tolerability result.
- **Every rate carries its denominator**, the safety denominators are labelled as the safety population rather than the randomised population, and the registered frequency threshold is stated so the non-serious event list reads as a floor rather than a census.

**Two bugs only live data could have found**, both of the same kind the project has hit before — a fixture encodes the same wrong assumption as the code, so unit tests pass while the feature is wrong:

1. **"Not completed" is not the same as "left".** NCT04368728 registers ~44,000 participants whose reason for not completing the blinded period is *"Participants entered open label period"*. Counted as attrition, that reads as **99.8% dropout on a trial whose real dropout was about 2%**. Fixed with a transition bucket alongside the death bucket.
2. **A results record's event groups are not the randomised arms.** KEYNOTE-189 registers five, three of them crossover and re-treatment cohorts — one with nine patients, one with two. Ranking events by the highest rate across all five put a 2-of-9 event at the top of a table where every visible column read 0.0%. Ranking and display now both use the groups with real denominators (anything under a tenth of the largest is excluded), so a nine-patient cohort cannot decide what the top row is.

A third, smaller one: an exactly-ten-point gap between two floating-point rates evaluates to `0.09999999999999999`, so a literal `>= 0.10` silently declined to fire on the clean case a threshold exists for. Every threshold comparison now goes through an epsilon.

**Results red flags** are a third, separate set — distinct from `decodeTrialRedFlags()` (the registered protocol) and `computeRedFlags()` (the user's own modelling inputs), and the UI says so. They cover: a primary registered but not posted, no between-group analysis registered for the primary at all, a primary interval that spans no-effect, a non-inferiority comparison, differential dropout ≥10 points between arms, ≥20% attrition in any arm, an AE-withdrawal gap ≥5 points, a serious-AE or death-rate gap between two arms, and results posted more than fifteen months after primary completion. Identical flags are stated once — a master protocol can otherwise raise the same sentence sixty times from one record.

**Verified**: `math_verification.js` from 724 to **793 checks**, all hand-derived, including regression tests built from the exact records that produced both live bugs. Full 10-file suite clean. Driven live in the packaged-equivalent Electron build against four real records — KEYNOTE-189, DAPA-HF, DECIDE and the 64-primary-endpoint BNT162b2 mega-protocol — plus a trial with no results, with **zero console errors** in every case and the rendering checked by eye in both a screenshot and the text tree.

## Open

### 🟡 Electron is 11 major versions behind (33.4.11, current is 44.x)
Found during a security-tooling pass. `npm audit` on `electron/` reports 14 vulnerabilities (13 high, 1 critical), all in packaging-time tooling (tar/node-gyp/electron-builder chain, real exposure ~zero — that tooling never runs for the end user) except Electron itself, which does carry real listed CVEs. Checked actual exploitability: the app never loads remote/untrusted content into any window (`win.loadFile()` on the local `rxnpv.html` only, never `loadURL` on anything external), so the large majority of Electron's own listed issues (which need malicious web content, cross-origin iframes, extensions, DevTools exposure) have no path to trigger here. Real risk is low; "11 versions behind" in a now-public repo is still a real hygiene item. `npm audit fix` (non-breaking) fixes nothing — every fix path requires a major version bump. Treat as its own isolated project (upgrade → full rebuild → full re-verify), not a quick patch. Not urgent given the actual exposure, but shouldn't sit forever.


### 🟡 112 engine functions have no independent hand-verified test, including some that touch real money numbers
A coverage re-audit (functions defined in the engine files vs. functions actually invoked by `test/math_verification.js`) found 91 of 205 verified, 112 not. Most of the 112 are either UI components (excluded from this count already), formatting helpers, or RNG primitives that aren't meaningfully unit-testable with an exact expected value — genuinely low priority. The real, worth-doing subset:
- **SEC EDGAR XBRL extraction** (`extractDilutedShares`, `extractSharesOutstanding`, `extractDebt`, `extractOptions`, `extractWarrants`, `extractConvertibleNotes`, `pickLatestUnit`, `calcRunwayFromFacts`) — these parse real government filing data structures straight into the capital-structure/dilution math. A wrong tag pick or wrong unit here would silently misstate a real company's actual share count or cash position. Highest-value gap found this pass.
- **`computeForwardRunway`** — genuinely notable: this exact function was the site of a real bug found and fixed via live testing earlier this session (conflated "no cash figure entered" with "cash flow turns positive before running out"), and it still has no permanent regression test pinning that fix. If it regresses, nothing will catch it automatically.
- **`solveImpliedPoSMultiplier` / `solveImpliedVariable`** — the Reverse-Solve tool's actual solving logic; user-facing "what does the price imply" outputs with no independent check.
- **`applyPartnershipToRevenue`, `applyBasePosAdjustment`, `distributeRnDCostByYear`, `computeRnDToLaunch`, `computePrelaunchSalesForceCost`, `aggregateCompanyRevenue`, `computeSOTPBreakdown`, `computeSensitivityDrivers`, `computeRedFlags`** — real valuation-affecting math/logic with no direct test.
- **`monthsBetween`, `parsePartialDate`, `median`** (in `ts_ctgovEngine.js`) — CT.gov trial-duration date parsing; partial-date edge cases (a study reporting "2024" vs "2024-06") are exactly where date math quietly goes wrong.
- **`treasuryMethodShares`** — exported in the test file's own EXPORTS list but never actually called/tested; looks covered at a glance, isn't.

### 🔴 PK/PD shows "half-life Infinityhr" when the elimination rate constant (Ke) is entered as 0
Ke=0 is a legitimate (if unusual) scientific input — a drug with literally zero elimination — and `halfLife(ke) = ln(2)/ke` is mathematically correct to return Infinity there. The bug is purely in the display: the raw JS value gets string-concatenated into `"...half-life Infinityhr"` instead of being formatted as something readable ("∞" or "no elimination (Ke = 0)"). Confirmed isolated to this one line — verified with a real dose that the concentration-time simulation, Cmax, AUC, and both charts all compute and render correctly even with Ke=0; nothing else cascades. Also notable: unlike every Trial Statistics tool (all of which reject invalid inputs with a "check your inputs" message before computing anything), PK/PD has no input validation at all — it will run and display whatever falls out, good or garbage.

### 🔵 PK/PD's total absence of input validation, more broadly
Related to the item above but broader: every Trial Statistics tool validates its inputs (N > 0, events between 0 and N, confidence level between 0 and 1, etc.) before computing, consistently. PK/PD validates nothing — dose, Ka, Ke, Vd, F, EC50, Hill can all be zero, negative, or blank and the simulation just runs, producing whatever comes out (sometimes correct-looking, sometimes silently wrong, as with the half-life case). Worth deciding deliberately whether PK/PD should adopt the same validate-first convention as the rest of Simulation, or whether that's overkill for a tool whose whole framing is "type in parameters from a paper."

### 🔵 A program that fails to compute drops out of the company valuation rollup with no visible sign anything went wrong
Audited all 14 empty `catch (e) {}` blocks in `src/` against the project's own stated rule ("never silently swallow a failure a user would care about"). 13 of 14 are genuinely fine on inspection: cache reads (`ctgovEngine.js`, `edgarEngine.js`) and a storage-cleanup routine (`helpers.js`) fall back to empty/partial on corrupt data, which is safe because the underlying source (CT.gov, EDGAR) is always re-fetchable; three others (`toolsView.js:1209`, `toolsView.js:1233`, `reportView.js:358`) are a deliberate, one already comment-explained, "don't let one broken program hide a whole comparison chart/export" guard on supplementary (not headline) numbers; `programEditor.js:129` is the same pattern but scoped to a single P&L panel for the program the user is actively editing in that moment — lower risk since a missing chart on the screen you're looking at is more likely to be noticed than a silent gap in an aggregate computed elsewhere.

The one real exception: in `caseShell.js`, each program's revenue result is computed inside a try/catch, and if it throws (a malformed or mid-edit incomplete program), that program is silently filtered out of the **company-level rollup** — the headline valuation number, not a supplementary chart. The rest of the company still computes and displays normally (correct degrade-gracefully behavior), but nothing tells the user a program was dropped — the case's total valuation would just be quietly lower than it should be, no red flag, no console warning, nothing visible. Not confirmed to have ever actually happened on a real case (a malformed program is an unusual state), but the failure mode is silent by design right now. Worth deciding: should `computeRedFlags` (or something equivalent) check for and surface "N programs failed to compute and were excluded"?

## Verified clean this pass — checked, not just assumed

- **The catastrophe-recovery story is real**: a completely fresh `git clone` of the public repo, on its own, with zero connection to the working project folder, builds, packages, and launches a working app. Confirmed by actually doing it, not by trusting the file list.
- **IPC/security boundary between the renderer and the OS is already done right**: `edgar:fetch` is hostname-locked to `sec.gov`, `open-external` is scheme-locked to `http(s)` only. No arbitrary file/URL access exposed to the renderer.
- **No injection risk in chart rendering**: the one `innerHTML`-setting code path in the whole app only ever receives output from the chart-render functions, and every one of those functions runs its text/label content through `escapeXml` before building the SVG string. No `dangerouslySetInnerHTML`, no `eval`, no `new Function` anywhere in the shipped app.
- **No dead code beyond the one item above** — re-checked with word-boundary matching after an initial naive check produced ~80 false positives (functions referenced only as bare identifiers passed to `h(Component, ...)` or through a dispatch table, which a naive "is it ever followed by `(`" search misses entirely).
- **No TODO/FIXME/HACK comments left anywhere in the shipped source.**
- **Zero duplicate entries** across all three comps databases (M&A: 68, Peak Sales: 38, Licensing: 15 — corrected counts; an earlier pass this same session had momentarily written 75 for M&A into `CLAUDE.md`, caused by a naive text search for `acquirer:` picking up a separate, unrelated 7-deal table (`SIMPLE_MULTIPLE_PRECEDENTS`) that happens to share that field name.

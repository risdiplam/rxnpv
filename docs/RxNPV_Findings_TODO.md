### 🟡 No Content-Security-Policy anywhere in the app
Neither `shell.html` (and therefore `electron/rxnpv.html`) nor `electron/main.js` sets a CSP, via `<meta http-equiv="Content-Security-Policy">` or the `session.defaultSession.webRequest` header approach. This sits on top of an otherwise correctly hardened `BrowserWindow` (`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, confirmed by reading `main.js` directly — no `webSecurity: false`, no `allowRunningInsecureContent`, no dev-tools auto-open in the shipped code), so the real exploitability is low given there's also no known injection point (chart rendering already confirmed to `escapeXml` everything, no `innerHTML` from untrusted data, no `eval`/`new Function` anywhere). But it's a real, standard hardening gap worth naming precisely: the renderer makes live `fetch()` calls directly to three external hosts with no proxy — `clinicaltrials.gov` (`ctgovEngine.js`), `api.fda.gov` (`fdaEngine.js`) — while only EDGAR is proxied through the main process (`edgar:fetch`, hostname-locked to `sec.gov`). A CSP `connect-src` allowlisting exactly those three hosts (plus `'self'` for the local file) would be defense-in-depth against a hypothetical future injection point being able to exfiltrate data anywhere on the internet, even though no such point exists today.

### 🔴 The packaged app cannot launch at all without an internet connection — React itself loads from a public CDN at runtime
`shell.html:219-220` loads React and ReactDOM via `<script src="https://unpkg.com/react@18/umd/react.production.min.js">` / `react-dom@18/...` — real network requests to a third-party CDN, made every time the app starts, not just for the live-data Tools. `electron/package.json`'s packaged `files` list is only `main.js`, `preload.js`, `rxnpv.html` — no local copy of React is ever bundled into the shipped `.app`. Confirmed this is genuinely load-bearing, not incidental: `test/setup.js` has to explicitly swap these CDN tags for a locally-installed React build specifically so the test suite can run without network access (per `test/README.md`) — meaning the project's own tooling already had to work around this exact problem for testing, but the shipped app was never given the same fix.

Concrete consequence: if the user opens RxNPV with no internet connection (offline, airplane mode, unpkg.com down or rate-limiting, a captive-portal Wi-Fi login screen not yet completed), the two `<script>` tags fail to load, `React`/`ReactDOM` are undefined, and the entire inline script — including `ErrorBoundary` itself, which is a React component — cannot run. The result is a blank white window with no error message the user would ever see (only a console error, invisible in a production, DevTools-closed build). This directly contradicts the app's whole premise as a **local, personal, catastrophe-proof desktop tool** — a user with no connectivity cannot open even their own already-saved cases, let alone do any new work, despite all of that being purely local computation with no live-data dependency. Also notable: pinned only to the `@18` major version, not an exact release, so the exact React build actually running is whatever unpkg happens to resolve `@18` to at launch time — not reproducible or pinned the way every other dependency in this project is.

This is the same root cause category as the "no CSP" finding below, and makes it more concrete: the app already has one real, unconditional third-party script-loading dependency in its trust chain (not just a hypothetical future one), which is exactly the kind of thing a CSP's `script-src`would exist to constrain if the app ever needs to keep loading from a CDN, and exactly the kind of thing bundling React locally would eliminate entirely. Given this project's whole philosophy is local-first reliability, vendoring the same `react.production.min.js`/`react-dom.production.min.js` files into `electron/` and pointing `shell.html` at the local copy seems like the more consistent fix over adding a CSP that merely tolerates the CDN dependency — but that's a call for the regroup, not something to decide mid-audit.

### 🔴 A live-API outage looks identical to "no data found" across all three external integrations — a real risk for an investing tool
Found via a direct read of every live-data tool's fetch/error-handling code (Company Lookup, Trial Explorer, Catalyst Calendar, FDA Lookup). In every case, a genuine network/API failure is caught and silently converted into the same UI state as "there is genuinely nothing here" — which for a retail investor using this to check things like insider transactions or drug approval status is a real, decision-relevant failure mode: absence of evidence (the API happened to be down) reads as evidence of absence ("no insider transactions," "drug not found").
- **FDA Lookup is the worst of the four**: `search()` (`toolsView.js:1706-1794`) uses `Promise.allSettled` but only ever reads the `"fulfilled"` branch — there is no `error` state anywhere in the component and no code path handles a `"rejected"` result. The underlying fetchers (`ts_fdaEngine.js`, via `tsFdaFetch`) **throw** on any non-404 failure rather than returning `{ok:false}`, so a thrown rejection just leaves `approval`/`label`/`adverseEvents` at their initial `null` — which renders the exact same "No openFDA data found for that name. Try the exact brand or generic name" message a real not-found gets. `tsFdaFetch` also has no timeout/`AbortController` at all, unlike its sibling `fdaFetch` — a hung request leaves the button stuck on "Searching…" forever with no fallback.
- **Company Lookup / EDGAR** (`edgarEngine.js`): `findCIK` (`:176-216`) catches every failure mode — genuine "no such company," a CIK-master-list network failure, an EFTS lookup exception — into one `return null`. `pullEdgarFinancials` then always shows the same "Could not find a CIK for `<name>`. Try the exact legal name, ticker, or enter a CIK manually," whether the company doesn't exist or SEC's servers are down. Same collapse in `fetchCompanyFacts` (`:231-242`) → the equally generic "Found CIK ... but couldn't retrieve financial data." This affects Company Lookup, the FDMC tool's "Pull from EDGAR," and Cash Runway's EDGAR pull — all three route through the same function.
- **Catalyst Calendar** (`toolsView.js:1552-1690`): per-program/per-case failures are dropped rather than aggregated into the top-level error state — `trialResults.forEach` silently `return`s on a failed CT.gov call (`:1578-1579`), the EDGAR catalyst-filing pass wraps each case in its own try/catch returning `hits: []` on any exception (`:1608-1615`). If every underlying fetch fails at once (a real outage), the user just sees "No future-dated trial completion estimates found for these programs" — indistinguishable from a genuinely quiet calendar.
- Fix shape is the same across all three: catch-and-return `{ok:false, error}` (the pattern `ctgovEngine.js`'s `check()` already uses correctly) instead of collapsing into `null`/`[]`, and surface a distinct "couldn't reach [SEC/CT.gov/openFDA] — try again" state wherever "not found" is currently the only negative state.

### 🟡 Four live-search handlers have no protection against out-of-order responses
Company Lookup's `search()`/`searchCompetitors()` (`toolsView.js:269-289`), Trial Explorer's `searchComps()`/`check()` (`:1815-1841`), Catalyst Calendar's `pullEvents()` (`:1564-1624`), and FDA Lookup's `search()` (`:1715-1729`) all fire a fetch and later call `setState` with the result, with no request-id/generation counter and no `AbortController` cancellation of the previous in-flight call. Concrete scenario: search "Moderna," realize you meant "Merck," and search again before the first request returns — if Moderna's response happens to resolve after Merck's (plausible: different companies, different response sizes, ordinary network jitter), the screen ends up showing Moderna's data while the search box still says "Merck," with no indication anything is wrong. Same fix shape across all four: a `let seq` counter (or `AbortController`) captured at call time, checked before the corresponding `setState` fires.

### 🔴 PK/PD shows "half-life Infinityhr" when the elimination rate constant (Ke) is entered as 0 — confirmed live on the packaged app
Reproduced directly on `/Applications/RxNPV.app`: dose 500mg, Ka=1, Ke=0, Vd=50 produces the headline **"10.00 mg/L — Cmax at t=37.44hr • half-life Infinityhr • AUC (window) 470.0 mg·hr/L"**, with everything else in that line reading normally.
Ke=0 is a legitimate (if unusual) scientific input — a drug with literally zero elimination — and `halfLife(ke) = ln(2)/ke` is mathematically correct to return Infinity there. The bug is purely in the display: the raw JS value gets string-concatenated into `"...half-life Infinityhr"` instead of being formatted as something readable ("∞" or "no elimination (Ke = 0)"). Confirmed isolated to this one line — verified with a real dose that the concentration-time simulation, Cmax, AUC, and both charts all compute and render correctly even with Ke=0; nothing else cascades. Also notable: unlike every Trial Statistics tool (all of which reject invalid inputs with a "check your inputs" message before computing anything), PK/PD has no input validation at all — it will run and display whatever falls out, good or garbage.

### 🟡 The Therapeutic Area dropdown offers near-synonym pairs that resolve to a generic fallback instead of the specific benchmark that actually exists
`THERAPEUTIC_AREAS` (`data.js:369-372`, the dropdown a program's Therapeutic Area field is built from) is a 23-entry union of the naming conventions used by three separate benchmark tables that don't share one taxonomy: `POS_BY_AREA` uses "Neurology"/"Autoimmune"/"Infectious disease"/"Urology", while `TRIAL_DURATION_BY_AREA`/`TRIAL_COST_BY_AREA` use "CNS"/"Immunomodulation"/"Anti-infective"/"Genitourinary" (plus "Renal") for the same underlying disease areas. The lookup functions themselves are correctly designed (`getPosForArea`/`getTrialCostForArea`/`getTrialDurationForArea`, `helpers.js:29-44`) — each explicitly checks for a match and falls back to a documented, source-labeled generic average (`matched: false`, source string reads "no specific data for this area") rather than silently returning garbage, and that fallback is exactly the shape `BenchField` is built to display. So this **isn't a silent-wrong-number bug** — it's a real, if softer, gap: a user who picks "Neurology" from the dropdown (the more natural term) gets the generic weighted-average Trial Duration and Trial Cost benchmark, even though a CNS-specific one exists in those same tables — it's just filed under a name the dropdown also happens to offer as if it were a distinct choice. Same for Autoimmune/Immunomodulation, Infectious disease/Anti-infective, and Urology/Genitourinary-or-Renal. Fix shape: either collapse the dropdown to one canonical name per area with the other kept only as an internal alias, or add an explicit alias map at the top of each lookup function.

### 🟡 Sum-of-the-Parts breakdown doesn't tax-shield corporate G&A the way the main valuation does, despite a comment claiming the two are "guaranteed consistent"
`computeSOTPBreakdown` (`scenarioEngine.js:287-313`) computes each program's own NPV after-tax (correctly reusing `applyTaxToCalendar`), but its separate G&A-drag term is built from the raw, pre-tax G&A dollar figure and discounted directly (`computeNPV(gaOnlyCF, ...)`) — never routed through `applyTaxToCalendar`. The main combined valuation (`computeCaseValuation`), by contrast, nets G&A against revenue *before* computing tax, so G&A gets a real tax shield there. Hand-derived example (21% tax rate, single year, $100M product contribution, $20M corporate G&A): the real combined calculation gives after-tax FCF of $63.2M ($100M−$20M=$80M pretax, taxed once at 21%); SOTP's calculation gives $59M ($100M taxed alone to $79M, minus the full untaxed $20M G&A) — a $4.2M understatement in this single-year example, equal to `taxRate × G&A` compounded across every year of a real multi-year discounted stream. Only manifests when `theCase.taxation.enabled = true` (off by default), but that's a real, user-facing toggle, and a multi-program case sophisticated enough to want a Sum-of-the-Parts breakdown is exactly the kind of case that would plausibly have tax modeling turned on too — a user would see the SOTP total not reconcile with the headline case valuation shown elsewhere, with the code's own comment (`scenarioEngine.js:284-286`) incorrectly asserting they're "guaranteed consistent." Confirmed no double-counted G&A (the per-program NPVs correctly zero out G&A via `zeroGA`, and the real G&A is subtracted exactly once via the separate stream) and confirmed the function correctly reuses the same shared valuation primitives the main DCF path uses rather than a separate, driftable reimplementation — this is specifically a tax-timing bug, not a structural one.

Also noted (documentation-location mismatch, not a bug): CLAUDE.md attributes "a stage-aware warning when a Simple Multiple pulled from post-approval M&A comps is applied to a pre-approval program" to the red-flags system — that warning actually lives as a separate, unconditional note in `valuationPanel.js:234-248`, not as one of `computeRedFlags`' six actual checks. Someone auditing "every red flag" by reading only `computeRedFlags` would miss it. All six of `computeRedFlags`' real checks (PoS-override-vs-benchmark, COGS-override-vs-modality, R&D-timeline-override, peak-share-vs-order-of-entry, compounded PoS-modifier stacking, runway-vs-nearest-catalyst) were hand-verified this pass with both a trigger case and a near-miss non-trigger case each — all six fire in the correct direction, none fires on pure-benchmark defaults, and every boundary value lands on the conservative "stay silent" side. `aggregateCompanyRevenue` was also hand-verified against the exact calendar-misalignment scenario CLAUDE.md's own history warns about (a later-launching program's own year-1 revenue correctly lands in the right company-calendar year, not naively index-matched) and confirmed correct — reinforced by the fact that cost and DCF rollups use the identical alignment formula, so a bug here would necessarily also surface there.

### 🔴 A user-typed "Launch in year" that diverges from the program's own R&D timeline can silently zero out — or badly mis-time — all remaining R&D cost
`distributeRnDCostByYear` (`dcfEngine.js:21-43`) spreads a program's remaining R&D cost items across calendar years using an array sized by `launchYearOffset` (`years`). The problem: `launchYearOffset` and the R&D item timeline it's supposed to match are two independently-settable things. `resolveLaunchYearOffset` (`rdEngine.js:78`) uses either the user's own free-typed "Launch in year (from today)" number field (`programEditor.js:186-188` — a bare number input whose own inline placeholder text literally suggests typing **0** for "launches immediately," per `programEditor.js:19`) or the computed R&D timeline — but `riskAdjItems[].years` (the actual remaining-cost breakdown from `computeRnDToLaunch`) is always derived independently from the R&D section, which has its own separate, optional "Apply" step (`programEditor.js:220-227`) the UI doesn't require or default to. Nothing keeps these two in sync.

Two concrete failure modes when they diverge:
1. **Cost gets dumped into the wrong year.** A Phase 2 program with a real ~8.15-year/$55.6M remaining R&D timeline, where the user types `launchYearOffset = 2` (plausible — they've seen guidance suggesting a faster launch than the benchmark implies, without separately touching the R&D override): only ~$7.9M of cost falls naturally within the 2-year window, and the function's own shortfall-recovery logic dumps the entire remaining ~$47.7M into year 2 alone, rather than years 3 through 9 where it actually belongs. Total dollars are conserved, but a DCF discounts each year separately — this materially mis-prices the cost's present value and distorts the mid-project cash-flow shape shown to the user.
2. **Cost silently vanishes entirely.** If `years` rounds to exactly 0 (e.g. `launchYearOffset = 0`, the value the UI's own placeholder text explicitly suggests for "launches immediately," on a program that still carries real remaining R&D cost), the function hits its own early-return guard (`dcfEngine.js:26`, `if (!years) return out;`) and returns an **empty array** before any allocation runs — its own comment acknowledges the risk ("caller should ensure launchYearOffset > 0 if there's R&D cost") but no caller actually enforces it. `computeCompanyRiskAdjustedCF` then simply has no cost to index for any calendar year, so the entire remaining R&D spend drops out of the cash-flow calendar with zero warning — overstating NPV by the full omitted cost. This is the same bug class CLAUDE.md documents as already fixed once for launch-year revenue indexing ("a fractional-launch-year bug silently zeroed cash flows"), recurring here on the R&D-cost side instead.

**Verified correct, same pass**: `distributeRnDCostByYear`'s core allocation math when `years` and the R&D timeline ARE consistent (a $60M/3-year item splits exactly $20M/$20M/$20M; a fractional 2.5-year phase correctly recovers its partial final-year share via shortfall recovery rather than dropping it — the opposite of the bug above); `computeRnDToLaunch` (hand-verified against a full Oncology Phase 2 example: $55.6M/8.15yr, correctly excludes already-completed Phase 1, correctly shrinks to just the remaining stretch for a program already filed or approved, no negative durations); `computePrelaunchSalesForceCost` ($8.4M for 100 specialty reps at 30% pre-launch staffing, matching its own documented single-year step-ramp design exactly — not a bug, the UI copy ("ramps to 30% one year before launch") accurately describes what it does); and dollar-unit consistency throughout the whole chain (millions vs. raw dollars, one clean conversion point, no mixed-unit bug).

### 🔴 A royalty deal has zero effect on the numbers in the app's own default mode, and Simple Multiple valuation silently drops upfront/milestone value entirely

### 🟡 Chart rendering: negative values break two chart types, plus smaller axis/single-point issues
A hand-verification pass on every chart-rendering function in `chart.js`/`ts_chart.js` (injection-safety already confirmed clean in an earlier pass — this was purely about rendering correctness at data extremes) found most functions correctly guard against empty data, single points, and identical values (domain floored via `Math.max(..., 1)`/`|| 1` patterns throughout) — the real findings are narrower:
- **`ScatterChart` (`chart.js:121`, used for the M&A Premium comps scatter) mishandles all-negative data.** `maxX = Math.max(...xVals) * 1.15 || 1` — the `*1.15` padding assumes a positive max; if every x (or y) value is negative (a real possibility here — a deal struck at a negative premium is a real, if unusual, M&A outcome the comps table itself could contain), multiplying a negative max by 1.15 pushes it *more* negative, so `maxX < minX`. Consequence: with one negative point, the axis silently inverts (the right-edge label reads a more-negative, nonexistent "max"); with several, the true max can exceed the computed one and that point plots outside the chart's own margin. `RevenueChart` in the same file already has the correct fix for this exact bug class (`minV = Math.min(0, ...)`) — `ScatterChart` just doesn't share it.
- **`renderLineChart` (`ts_chart.js:117`, used across Simulation) hard-codes `yMin = 0`.** Any negative y-value maps below the intended plot area, potentially clipped by the SVG's own bounds and invisible, with the axis ticks never reflecting the excursion — a real regression relative to the fix already applied in `chart.js`'s `revenueChartYScale`. Also in the same function: **a single-point series renders as a blank chart** — the SVG path is just one `M x,y` with no `L` command to draw, so nothing appears except an invisible (opacity-0) hover target.
- **`renderHistogram` (`ts_chart.js:44`) mislabels its x-axis for a single-value/all-identical dataset.** The div-by-zero guard (`range = max - min || 1`) correctly prevents NaN, but the middle tick is still computed off the fallback range of 1 rather than the true range of 0 — for a dataset that's entirely the value 100, the three x-axis ticks render as **"100, 100.5, 100"**, a non-monotonic, misleading label sequence.
- **`renderForestPlot` (`ts_chart.js:309`, the newer shared primitive used across the 2×2/Non-Inferiority/Meta-Analysis tools) has two gaps**, both latent (not reachable from any of its current 10 call sites in `ts_app.js`, which all supply at least one row or a reference line — worth knowing about since it's an exported shared primitive other code could call differently later): calling it with zero rows and no `pooled`/`referenceLine`/`marginZone` produces `Infinity`/`-Infinity`/`NaN` domain values, which corrupt the three axis-tick labels into literal `"NaN"`/`"InfinityB"` text or invalid SVG (dropped elements) — everything else on the chart still renders; and a malformed pooled-estimate row where `lower > upper` draws a self-intersecting "bowtie" polygon instead of the intended diamond shape (coordinates stay finite, just visually wrong). A `lower === upper` degenerate CI, and a malformed non-pooled row, were both confirmed already handled correctly.
- **Confirmed correct, same pass**: `revenueChartYScale`/`RevenueChart`, `RiskWaterfallChart`, `PeakSalesCompsChart` (all in `chart.js`); `niceTicks`, `formatTick`, `renderTornadoChart` (empty-safe, no crash, though it renders a blank-but-valid chart with no explicit "no data" message for zero rows — a soft gap, not a bug), and `renderIconArray` (`ts_chart.js`) — the last of these is genuinely robust: even a malformed/NaN `fraction` input can't produce an invalid coordinate, since the dot grid geometry never depends on it.

### 🔴 EDGAR extraction has multiple real bugs that silently misstate a real company's actual cash runway, share count, and debt — the highest-severity findings of this entire audit
A full hand-verification pass on all eight EDGAR XBRL extraction functions in `edgarEngine.js` (previously flagged as having zero test coverage despite feeding real money numbers straight into capital-structure/dilution/runway math) found several concrete, realistically-triggered bugs, each with a hand-constructed fixture proving it:

1. **`calcRunwayFromFacts` (~line 244) — runway can be off by roughly 2-3x, silently, on most Q2/Q3 pulls.** The function selects the latest operating-loss fact by filtering on `form === "10-Q"` and `fp.startsWith("Q")`, then sorting by `end` date — but every mid-year 10-Q reports its income statement for BOTH the standalone quarter AND the year-to-date period under the *same* tag, with the *same* `end` date (e.g. "3 months ended 6/30" and "6 months ended 6/30" both end 6/30). The code never checks `start`, so a tie on `end` is resolved purely by whichever entry EDGAR happens to list first. Hand-constructed fixture: a Q2 filer with a 6-month YTD operating loss of $24M and a standalone Q2 loss of $12M, $60M cash — correct runway is $60M ÷ ($12M/3) = **15.0 months**; depending on array order, the function can instead divide the $24M *6-month* figure by 3 (as if it were a 3-month figure), yielding **7.5 months** — exactly half the right answer, with no error or flag. This reproduces for essentially any Q2/Q3 pull, not a rare edge case. Same class of bug as the historical "~1,000,000x dilution" bug CLAUDE.md documents, just on the duration axis instead of the scale axis.
2. **`extractConvertibleNotes` (~line 383) — sums nothing, stops at the first matching tag.** Unlike `extractDebt` (which correctly sums across multiple matching tags), this one loops through fallback tag names and `break`s on the first non-null hit. Real convertible notes are routinely split into current/noncurrent portions under two different tags simultaneously. Fixture: $5M current + $15M noncurrent convertible notes (a real, common balance-sheet split) — correct total is $20M; the function finds noncurrent first, returns **$15M**, silently dropping the $5M current portion (a 25% understatement). Also: the fallback chain has `ConvertibleDebtNoncurrent` but no matching `ConvertibleDebtCurrent`, an asymmetric gap that would return a partial/zero result for a filer using that tag family with only a current-portion balance.
3. **`pickLatestUnit`/`extractWarrants`/`extractOptions` (~lines 356/365/374) — undercounts any multi-tranche issuer.** Same tie-on-`end`-date problem as #1: if a company reports two dimensioned tranches under one tag with the same date (e.g., public warrants and private-placement warrants both tagged `ClassOfWarrantOrRightOutstanding` — very common for de-SPAC biotechs), the function returns only one tranche, not the sum. Fixture: 5,000,000 public + 3,333,333 private warrants (total 8,333,333) — function returns just one of the two, e.g. **5,000,000**, a ~40% undercount. Separately, `pickLatestUnit`'s own name/comment implies genuine cross-unit reconciliation ("pick the latest across units"), but it actually just picks the first non-empty unit array by a fixed type-priority (`shares` → `USD` → `USD/shares` → `pure`) and never compares recency across unit types — low practical exposure since a compliant filer's tag type usually constrains this to one unit anyway, but the function doesn't do what its name says.
4. **`extractSharesOutstanding` (~line 306) — fallback chain ranks period-average (flow) tags above a genuine point-in-time balance, and skips the form filter every sibling function applies.** The priority list ranks `WeightedAverageNumberOfShareOutstandingBasicAndDiluted`/`WeightedAverageNumberDilutedSharesOutstanding` (EPS-denominator, time-weighted averages over a reporting period) ABOVE `CommonStockSharesIssued` (an actual point-in-time balance), and applies no `10-Q`/`10-K` form filter (unlike `extractDilutedShares`, which does). Fixture: a micro-cap that doubles its share count mid-quarter via a raise (20M→40M), where the weighted-average tag reads 26.5M and the period-end issued-shares tag reads the correct 40M — the function returns **26,500,000**, a 34% understatement of actual current share count, feeding directly into per-share and market-cap math. This is exactly the scenario (a recent capital raise) where getting the current share count right matters most.
5. **`extractDebt`** shares the same intra-tag tie-break blind spot as #3 for a multi-tranche debt structure (e.g., layered venture-debt facilities), though it's architecturally sound otherwise (it does correctly sum across different tag *names*).

**Confirmed correct, same pass**: `extractDilutedShares`'s tag-priority ordering (correctly favors the tags biotechs actually file, given GAAP requires diluted=basic EPS for loss-making companies); dollar-value unit handling across all eight functions (confirmed raw-USD throughout, no rescaling bug — the historical 1,000,000x bug class does *not* recur here on the scaling axis, only on the duration-selection axis in #1); and missing-concept handling (every function cleanly returns `null` rather than throwing when EDGAR's response lacks a concept entirely — a foreign private issuer with no options/warrants XBRL data doesn't crash the whole EDGAR pull).

This is the highest-confidence, most concretely-reproducible set of bugs found in this entire audit — each one has a specific, realistic fixture (not a contrived adversarial input) and a clear silent-wrong-number consequence on real company data a retail investor would actually rely on. Recommend prioritizing #1 (runway) and #4 (shares outstanding) first, since both are commonly-hit scenarios (any Q2/Q3 filer; any company that raised capital recently) rather than requiring an unusual capital structure.

### 🟡 A negative option/warrant strike price can manufacture more diluted shares than the option pool itself contains
`treasuryMethodShares(count, strike, currentPrice)` (`capitalEngine.js:11-17`, shared by both the Options and Warrants dilution inputs) guards `count <= 0`, `currentPrice <= 0`, and `strike >= currentPrice` (the standard "out of the money" check) — but never guards `strike < 0`. Hand-verified: 1,000,000 options at strike **−$10**, price $40 → `proceeds = 1,000,000 × −10 = −10,000,000`, `buybackShares = −10,000,000 / 40 = −250,000`, net new shares = `1,000,000 − (−250,000) = 1,250,000` — a diluted share count that exceeds the entire 1,000,000-option pool, which is mathematically impossible for the treasury-stock method (net new shares from TSM can never exceed the option count). Nothing currently stops this: the "Options avg strike"/"Warrants strike" fields are plain `<input type="number">` with no `min` (`valuationPanel.js:393,395`), and an EDGAR-pulled strike value flows through the same function unsanitized (`toolsView.js:301-303`). `ifConvertedShares` — the analogous function for convertible notes right next to this one — already correctly guards its equivalent negative-input case, so this is an inconsistency between two sibling functions rather than a systemic gap. Real-world trigger requires an invalid/typo'd strike entry (a stray minus sign), not a normal well-formed input, so this is lower-likelihood than the historical unit-conversion bugs CLAUDE.md documents — but the failure mode (silently overstating diluted share count, understating per-share fair value) is exactly the class of thing this project's math-verification discipline exists to catch. Fix: add a `strike < 0` guard mirroring `ifConvertedShares`'s existing pattern. (Everything else in `capitalEngine.js` — `ifConvertedShares`, `computeCapitalStructure`'s unit consistency across basic/options/warrants/convertible/cash/debt, `computeEquityValue`, `applyFutureRaise`, and its composition with `computeDilutionPath` — was hand-verified against worked examples this pass and found correct; see "Verified clean" below.)

### 🟡 Custom comp entry silently converts a blank/invalid numeric field to zero, with no warning, and merges it into the same array as verified data
`CustomCompForm` (`helpers.js:428-454`) only requires the *first* field to be non-empty before allowing Save — every other field, including the core numeric ones, is unvalidated. The parse functions that run on save make this concrete: `parseMaVals` (`toolsView.js:111-118`) does `valueB: parseFloat(vals.valueB) || 0`, and the same `parseFloat(...) || 0` pattern repeats for `peakSalesB` (custom Peak Sales comps, `:1163`) and `upfrontM`/`totalDealValueM` (custom Licensing comps, `:1397`) — a blank, non-numeric, or accidentally-zero entry in any of these fields is silently accepted and saved as a real `0`, indistinguishable from an intentional zero.
